> **Ранняя стадия.** Работает: unary-нагрузка на настоящий сервис, несколько методов со своим
> RPS в одном прогоне, поиск точки отказа, разные данные в каждом вызове (`dataset`), несколько
> соединений, отчёт в консоль и JSON для скриптов. Ещё нет:
> разгона, порогов pass/fail для CI, экспорта метрик — **[что будет дальше →](docs/ru/roadmap.md)**.
> Не хватает возможности — [напишите issue](https://github.com/yhgrwav/leettest/issues/new/choose).
> Ниже описано только то, что уже работает.

Инструмент отвечает на вопрос, с которым приходят к нагрузочному тесту: **при какой нагрузке
сервис перестаёт справляться и где узкое место.** Он даёт нагрузку, похожую на настоящую, —
несколько методов одновременно, у каждого свой RPS, — и меряет так, чтобы числа не врали, когда
сервис деградирует. Ни `.proto`, ни кодогенерации, ни скриптов.

Приоритеты, по порядку: числа не врут; инструментом удобно пользоваться — неясное сообщение об
ошибке такой же дефект, как неверное число; генератор не становится узким местом.

## Установка

```console
$ go install github.com/yhgrwav/leettest/cmd/leettest@latest
```

Нужен Go 1.26 или новее. Готовые бинарники — на странице релизов.

**Где запускать.** На Linux рядом с целью: в той же сети, в том же кластере, на раннере CI. Всё,
что лежит между генератором и целью, входит в латенси и выглядит как время цели: на нашем стенде
при 1000 RPS через проброс портов Docker Desktop p99 был 38 мс, внутри сети Docker — 2 мс. Точное
расписание вызовов — только на Linux; в контейнере с квотой CPU меньше двух ядер возможны редкие
задержки старта до периода квоты (обычно 100 мс), отчёт их показывает. За L4-балансировщиком
нагружается один бэкенд — [см. ниже](#как-читать-отчёт). На Windows часы идут шагами около 0,5 мс, и прогон с быстрым
сервисом будет объявлен недействительным.

**[Быстрый старт →](docs/ru/quickstart.md)** — все возможности на эталонном стенде: конфиг со
всеми полями, чтение отчёта, разные поведения цели, CI. Работаете через ИИ-агента — дайте ему
[AGENTS.md](AGENTS.md).

## Запуск

```yaml
app:
  target:
    ip: localhost
    port: 50051
  tls: false

load:
  warmup: 5s
  calls:
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m

    - method: wallet.v1.WalletService/Transfer
      rps: 50
      duration: 1m
```

```console
$ leettest -c leettest.yaml
```

Имя метода — полное, `пакет.Сервис/Метод`. Схему метода инструмент берёт у сервиса через gRPC
server reflection, поэтому `.proto` не нужен. Конфиг, адрес, методы и тело запроса проверяются до
старта: любая ошибка — код 1 и ни одного вызова к цели. Первые `warmup` секунд не попадают в
статистику. Все вызовы метода уходят с одним и тем же телом: для записи с ключом идемпотентности
меряется путь повтора, а не создание записи. Другой запрос на каждый вызов — файл в `dataset`:
по JSON на строку, по порядку и по кругу. Все поля, TLS, заголовки, тело запроса и
флаги — в **[справочнике](docs/ru/reference.md)**.

В терминале прогон идёт в полноэкранном виде, `q` — остановить. Без терминала (CI, перенаправленный
вывод) — строка прогресса раз в секунду:

```
32.0s  sent 25600  rps 800  in-flight 47  failed 51  not-sent 0  p99 43ms
```

Отчёт идёт в stdout, прогресс и ошибки — в stderr. Без экрана (например, по ssh): `-plain`.

## Как читать отчёт

В конце — отчёт по каждому методу: отправлено, отказов, `sent/s`, p50/p90/p95/p99.

- Вызов считается от **запланированного** момента: если цель или генератор задержали его, это в
  латенси.
- `sent/s` — отправленные вызовы, делённые на время отправки: подвисание цели в конце прогона не
  занижает эту цифру.
- Перцентиль, на место которого могли попасть вызовы, оборванные таймаутом, печатается **нижней
  границей**: `>2.0s`. Это не значение, а «не меньше».
- Под методом с `dataset` стоит строка `data:`: сколько запросов файла использовано и
  сколько раз ушёл самый частый. Это не значит, что цель увидела столько разных запросов.
- По умолчанию нагрузка идёт по **одному соединению**, и оно попадает в **один бэкенд**: за
  L4-балансировщиком (Kubernetes ClusterIP, NLB) и когда DNS отдаёт несколько адресов. Вывод «не
  держит X» относится к этому бэкенду, а не к сервису, и отчёт этого не покажет. Чтобы нагрузить
  несколько, задайте `app.connections`: блок `Connections:` в отчёте покажет по
  строке на соединение — адрес, вызовы, долю отказов и p99, так что отстающий бэкенд виден.
  L7-балансировщик, который распределяет отдельные запросы (Envoy, gRPC-ингресс), раскидывает и
  одно соединение. Отчёт печатает, сколько раз соединение переподключалось и какой лимит
  одновременных стримов объявила цель.

**Категории.** Ответы, кроме успешных, разделены по строкам, у каждой свои перцентили. Статус мог
прислать не цель, а прокси перед ней: nginx без живого бэкенда отвечает `UNAVAILABLE`, и клиент
одно от другого не отличит.

- `request error` — вызов провалился бы при любом темпе: неверный запрос или запрос, который цель
  или прокси сочли слишком большим.
- `overload` — статус говорит «перегружен или недоступен»: `RESOURCE_EXHAUSTED`, `UNAVAILABLE`.
  Это слова статуса, а не диагноз цели.
- `failure` — статус говорит, что вызов сломался: `INTERNAL`, `UNKNOWN`, `DATA_LOSS`, `CANCELLED` от
  другой стороны, `ABORTED` (конфликт одновременных изменений, а не нехватка ёмкости).
- `bad response` — ответ пришёл, но клиент его не принял: больше `app.max_response_size` или сжат
  кодировкой, которую клиент не объявлял.
- `client error` — клиент сам отказался отправлять: запрос не закодировался, упал кодек или
  перехватчик.

Вызовы, не дошедшие до цели, считаются отказами, но в перцентили не попадают. Запрос, который ушёл,
но статуса не получил — другая сторона сбросила стрим или оборвала соединение, — считается
отдельно, как `cut off`: цель или прокси могли его обработать, для записи это повод проверить
дубли. Вызов, прерванный нашей остановкой (Ctrl+C, SIGTERM), — `aborted` при любом коде: это не
отказ цели.

| Код | Статус пришёл по сети | Код поставил клиент, запрос ушёл | Код поставил клиент, запрос не ушёл |
|---|---|---|---|
| `INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `UNAUTHENTICATED`, `FAILED_PRECONDITION`, `OUT_OF_RANGE`, `UNIMPLEMENTED` | `request error` | `cut off` | `client error` |
| `RESOURCE_EXHAUSTED` | `overload`; «larger than max» от grpc-go — `request error` | `cut off`; ответ больше нашего лимита — `bad response` | `client error` |
| `UNAVAILABLE` | `overload` | `cut off`; поток, отвергнутый целью до обработки, — `overload` | `unreachable`; то же |
| `CANCELLED`, `UNKNOWN`, `INTERNAL`, `DATA_LOSS`, `ABORTED` | `failure` | `cut off`; ответ не распаковался — `bad response` | `client error` |
| `DEADLINE_EXCEEDED` | тайм-аут | тайм-аут | тайм-аут, не отправлен |

Слишком большой запрос узнаётся по тексту ошибки grpc-go. Цель на другой реализации (Envoy, Java)
пишет его иначе, и такой отказ попадёт в `overload`, а не в `request error`.

`UNAVAILABLE` у отвергнутого потока — перевод grpc-go для RST_STREAM REFUSED_STREAM от цели: код
поставил клиент, а отказ прислала цель, поэтому он в строке «sent by the target». Такой поток цель
не обрабатывала (RFC 9113 §8.7).

Под отчётом упавшие вызовы разложены по кодам gRPC в две строки. «sent by the target» — статус
пришёл по сети, от цели или от прокси. «set by the client» — код поставил сам клиент: никто не
ответил, стрим сброшен, истёк наш дедлайн или клиент не принял ответ. `DEADLINE_EXCEEDED` от цели
обычно наш же дедлайн: он уходит цели в заголовке `grpc-timeout`. Категория говорит, чья это вина,
код — что искать в логах цели.

**Ожидания на стороне клиента.** В латенси входит всё, что вызов прождал у нас: опоздание
генератора, ожидание соединения, ожидание свободного стрима. Если без них p99 хоть одного метода
падает на 10 % и больше или часть вызовов так и не ушла, отчёт выносит вердикт и называет причину,
которая чаще других в хвосте p99, и печатает p99 без ожиданий — время, которое вызов провёл у цели.
Если причина — кончились стримы, ёмкость цели выше «лимит × соединения» не измерена. Если перед
вызовом ждали резолвер, в ожидание соединения попадают и интерсепторы вызывающего, поэтому p99 без
ожиданий может выйти немного заниженным. Неотправленные вызовы разбиты по причинам. Сдвиг меньше
10 % — не вердикт, а заметка с числом; если p99 — нижняя граница, сдвиг неизвестен, и заметки нет.

**Часы.** Инструмент меряет шаг часов хоста до и после прогона. Шаг заметен — печатается строка
`clock step 502us on this host: every latency and wait is +/- 502us`. На Linux шаг — десятки
наносекунд, строки нет.

## Когда прогон недействителен

Отчёт есть, но числа не про нагрузку на цель (код 2), если:

- **упёрся в потолок `-max-in-flight`.** Таймауты и потолок сверяются до старта так, что зависшая
  цель в него не упирается; упор значит, что генератору не хватило процессора.
- **все измеренные вызовы метода — `request error`, `client error` или `bad response`.** Заметка
  называет метод, причину и что делать.
- **часы хоста грубее четверти p50** какого-либо метода, или шаг вырос за прогон до 1 мкс и выше
  (`clock_step`). Мерьте с Linux.

## Коды выхода

Порогов «держит / не держит» пока нет, поэтому дошедший до конца прогон возвращает `0`, как бы
цель ни отвечала: **`0` не значит «сервис здоров»**. Коды ранжированы: недействительный прогон
(`2`) важнее неполного (`3`); остановка, которая напечатала отчёт, всегда `3`.

| Код | Что случилось |
|---|---|
| `0` | План выполнен, отчёт полный |
| `1` | Прогон не состоялся: флаги, конфиг, подключение. Отчёта нет |
| `2` | Прогон недействителен (см. выше). Отчёт есть, но числа не про нагрузку |
| `3` | Прогон остановлен раньше плана. Отчёт есть и покрывает только то, что успело пройти |
| `130` | Аварийный выход без отчёта после Ctrl+C |
| `143` | Аварийный выход без отчёта после SIGTERM |

Код `4` зарезервирован под пороги. Как работает остановка — в
[справочнике](docs/ru/reference.md#остановка).

## JSON для скриптов и CI

С `-output json` в stdout идёт ровно один JSON-объект и перевод строки; всё остальное — в stderr,
так что stdout можно сразу отдать `jq`. Объект печатается только для прогона, который состоялся
(коды `0`, `2`, `3`); при `1`, `130` и `143` stdout пуст. Поле `outcome` — `complete`, `invalid`
или `incomplete` — всегда совпадает с кодом выхода.

Схема версионируется полем `schema_version`, сейчас `1`, и это контракт; текст на экране — нет,
разбирайте JSON, а не экран. Правила:

- новое поле добавляется без смены версии; переименование, удаление или смена типа поля
  повышают `schema_version`;
- набор значений перечислений (`outcome`, `unchecked[].reason`, коды в `failure_codes`) может
  расширяться без смены версии;
- потребитель обязан пропускать неизвестные поля и обрабатывать неизвестное значение
  перечисления, не падая.

Единица — в имени поля: `_us` — целые микросекунды, `_s` — целые секунды; частота `rps` —
единственное дробное число. Значение, которого прогон не дал, — `null`, а не `0`. Перцентиль —
объект `{"us": 1234, "lower_bound": false}`: при `lower_bound: true` это нижняя граница, а не
значение. Задержки — значения гистограммы с точностью 3 значащие цифры (погрешность до 0,1%),
счётчики точные. Время отсчитывается от `started_at` (RFC 3339, UTC) — начала расписания, прогрев
включён; `duration_us` тоже включает прогрев. `in_flight` в секунде — сколько вызовов было в
полёте на её конце. Коды в `failure_codes` — канонические имена (`UNAVAILABLE`). Сверка: итоги прогона —
сумма итогов методов, а по секундам метода `Σ begun` плюс `outside_timeline` — все его вызовы,
включая прогрев.

Решения — полями, а не текстом: `invalid_reasons` (`in_flight_cap`, `nothing_measured`,
`clock_step`), `methods[].invalid_reason` (`request_error`, `client_error`, `bad_response`, `mixed`
или `null`), `tail_wait_cause` (`generator`, `stream`, `connection` или `null`) и числа по причинам
в `client_waits`. `notes` и `unchecked[].error` — текст для человека, он меняется свободно, не
разбирайте его.

Тишина цели: `methods[].silent_from_s` — секунда, с которой цель не ответила ни на один
отправленный вызов, `methods[].silent_sent_rps` — сколько вызовов ушло за секунду до неё,
`methods[].silent_planned_rps_low` и `_high` — плановый темп стадий в ту же секунду. Без тишины все
`null`; плановый темп `null` и тогда, когда в ту секунду стадий уже не было. `planned_rps_low` и
`_high` — темп всего плана.

Текстовый отчёт печатается только в ASCII. Символы извне ASCII — в имени метода, в тексте ошибки
от цели — печатаются как `\uXXXX` (за пределами U+FFFF — парой суррогатов, как в JSON). `notes` в
JSON несут тот же экранированный текст.

### Поиск точки отказа

Секция `load.breakpoint` вместо `rps` и `duration` у вызова: LeetTest поднимает нагрузку ступенями
и называет, на какой ступени цель держалась и на какой сломалась. Вызов — ровно один, без `rps`,
`duration` и `load.warmup`.

```yaml
load:
  calls:
    - method: wallet.v1.WalletService/GetBalance
      timeout: 500ms
  breakpoint:
    from: 100         # первая ступень, rps
    to: 2000          # выше не идём
    factor: 1.25      # следующая ступень = прошлая × factor; или step: 100 — на столько rps больше
    settle: 5s        # начало ступени, не идущее в вердикт; меньше половины hold
    hold: 30s         # длина ступени
    p99_limit: 200ms  # необязательно; без него ступень ломается на p99 больше 3× лучшей выдержанной
```

Ступень ломается, если не меньше 1% вызовов упали или p99 перешёл порог. Сломанная ступень
повторяется после паузы и, кроме первой, после проб на первой ступени: цель должна вернуться к
прежнему p99. Ступень засчитывается выдержанной, только если генератор отправил запланированное — не
меньше 99,9% вызовов окна измерения. Иначе это предел прогона, а не цели. До первой ступени в
stderr — строка `breakpoint: up to N steps, at most T`: сколько ступеней и сколько поиск займёт в
худшем случае. Соединение одно на весь поиск; если цель его рвёт, ступень сломана, переподключения
нет.

Итог (`outcome` в JSON) — закрытый список: `broke` (держала X, сломалась на Y), `broke_at_first`
(сломалась уже на первой ступени — начните ниже), `held_all` (выдержала всё до `to`), `run_limit`
(кончился генератор, лимит соединения или `-max-in-flight`: о цели выше ничего не известно),
`stopped` (Ctrl+C), `invalid` (ступень оказалась недействительным прогоном). Причина (`why`) —
тоже закрытый список: `errors`, `p99_limit`, `p99_vs_base`, `connection`, `no_recovery`,
`generator`, `in_flight_cap`, `stream_limit`, `stream_wait`, `clock_step`, `request_errors` или
`null`. `held_rps` и `broke_rps` — `null`, где их нет. В режиме поиска JSON — другой объект:
`mode: "breakpoint"`, полей обычного прогона на верхнем уровне нет, каждый прогон со своим полным
отчётом лежит в `breakpoint.runs` (`kind`: `step`, `repeat`, `probe`; `planned_rps` и `sent_rps`).
Обычный прогон пишет `mode: "run"`.

Коды выхода: `0` для `broke`, `broke_at_first`, `held_all`, `run_limit` — это находки; `2` для
`invalid`; `3` для остановки одним Ctrl+C.

Инструмент отвечает на вопрос, с которым приходят к нагрузочному тесту: **при какой нагрузке
сервис перестаёт справляться и где узкое место.** Он даёт нагрузку, похожую на настоящую, —
несколько методов одновременно, у каждого свой RPS, — и меряет так, чтобы числа не врали, когда
сервис деградирует. Ни `.proto`, ни кодогенерации, ни скриптов.

Приоритеты, по порядку: числа не врут; инструментом удобно пользоваться — неясное сообщение об
ошибке такой же дефект, как неверное число; генератор не становится узким местом.

Проект развивается: что работает уже сейчас — ниже, что будет дальше — в [плане развития](docs/ru/roadmap.md).

Так выглядит прогон: посреди нагрузки сервис замирает на три секунды — на экране копятся вызовы в
полёте, а отчёт считает те, что остались без ответа.

## Установка

Linux и macOS (amd64 и arm64) — одной командой:

```sh
curl -fsSL https://raw.githubusercontent.com/yhgrwav/leettest/main/install.sh | sh
```

Скрипт ставит последний релиз в `~/.local/bin`, сверяет контрольную сумму и, если этого каталога нет
в `PATH`, печатает строку для профиля shell. Windows — архив со
[страницы релизов](https://github.com/yhgrwav/leettest/releases/latest). Или через Go 1.26+:

```sh
go install github.com/yhgrwav/leettest/cmd/leettest@latest
```

Проверка: `leettest -version`. Если после `go install` команда не найдена —
`export PATH="$PATH:$(go env GOPATH)/bin"`.

**Где запускать:** на Linux рядом с целью — в той же сети, кластере или на раннере CI. Всё, что
лежит между генератором и целью, попадает в латенси. Подробнее — в [справочнике](docs/ru/reference.md#где-запускать).

**[Быстрый старт →](docs/ru/quickstart.md)** — все возможности на эталонном стенде: конфиг со
всеми полями, чтение отчёта, разные поведения цели, CI. Работаете через ИИ-агента — дайте ему
[AGENTS.md](AGENTS.md).

## Запуск

```yaml
app:
  target:
    ip: localhost
    port: 50051
  tls: false

load:
  warmup: 5s
  calls:
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m

    - method: wallet.v1.WalletService/Transfer
      rps: 50
      duration: 1m
```

```sh
leettest -c leettest.yaml
```

Имя метода — полное, `пакет.Сервис/Метод`. Схему метода инструмент берёт у сервиса через gRPC
server reflection, поэтому `.proto` не нужен. Сервис без reflection (с v0.3): схема из файлов `.proto` или protoset —
[`examples/proto.yaml`](examples/proto.yaml), поле `app.proto` / `app.protoset` в
[справочнике](docs/ru/reference.md). Конфиг, адрес, методы и тело запроса проверяются до
старта: любая ошибка — код 1 и ни одного вызова к цели. Первые `warmup` секунд не попадают в
статистику. Все вызовы метода уходят с одним и тем же телом: для записи с ключом идемпотентности
меряется путь повтора, а не создание записи. Другой запрос на каждый вызов — файл в `dataset`:
по JSON на строку, по порядку и по кругу (`dataset_order: random` — в случайном, seed в отчёте
повторяет порядок). Все поля, TLS, заголовки, тело запроса и
флаги — в **[справочнике](docs/ru/reference.md)**.

В терминале прогон идёт в полноэкранном виде, `q` — остановить. Без терминала (CI, перенаправленный
вывод) — строка прогресса раз в секунду:

```
32.0s  sent 25600  rps 800  in-flight 47  failed 51  not-sent 0  p99 43ms
```

Отчёт идёт в stdout, прогресс и ошибки — в stderr. Без экрана (например, по ssh): `-plain`.

## Как читать отчёт

В конце — отчёт по каждому методу: отправлено, отказов, `sent/s`, p50/p90/p95/p99.

- Вызов считается от **запланированного** момента: если цель или генератор задержали его, это в
  латенси.
- `sent/s` — отправленные вызовы, делённые на время отправки: подвисание цели в конце прогона не
  занижает эту цифру.
- Перцентиль, на место которого могли попасть вызовы, оборванные таймаутом, печатается **нижней
  границей**: `>2.0s`. Это не значение, а «не меньше».
- Под методом с `dataset` стоит строка `data:`: сколько запросов файла использовано и
  сколько раз ушёл самый частый. Это не значит, что цель увидела столько разных запросов.
- По умолчанию нагрузка идёт по **одному соединению**, и оно попадает в **один бэкенд**: за
  L4-балансировщиком (Kubernetes ClusterIP, NLB) и когда DNS отдаёт несколько адресов. Вывод «не
  держит X» относится к этому бэкенду, а не к сервису, и отчёт этого не покажет. Чтобы нагрузить
  несколько, задайте `app.connections`: блок `Connections:` в отчёте покажет по
  строке на соединение — адрес, вызовы, долю отказов и p99, так что отстающий бэкенд виден.
  L7-балансировщик, который распределяет отдельные запросы (Envoy, gRPC-ингресс), раскидывает и
  одно соединение. Отчёт печатает, сколько раз соединение переподключалось и какой лимит
  одновременных стримов объявила цель.

**Категории.** Ответы, кроме успешных, разделены по строкам, у каждой свои перцентили. Статус мог
прислать не цель, а прокси перед ней: nginx без живого бэкенда отвечает `UNAVAILABLE`, и клиент
одно от другого не отличит.

- `request error` — вызов провалился бы при любом темпе: неверный запрос или запрос, который цель
  или прокси сочли слишком большим.
- `overload` — статус говорит «перегружен или недоступен»: `RESOURCE_EXHAUSTED`, `UNAVAILABLE`.
  Это слова статуса, а не диагноз цели.
- `failure` — статус говорит, что вызов сломался: `INTERNAL`, `UNKNOWN`, `DATA_LOSS`, `CANCELLED` от
  другой стороны, `ABORTED` (конфликт одновременных изменений, а не нехватка ёмкости).
- `bad response` — ответ пришёл, но клиент его не принял: больше `app.max_response_size` или сжат
  кодировкой, которую клиент не объявлял, или нарушает унарность: OK без сообщения или лишнее
  сообщение.
- `client error` — клиент сам отказался отправлять: запрос не закодировался, упал кодек или
  перехватчик.

Вызовы, не дошедшие до цели, считаются отказами, но в перцентили не попадают. Запрос, который ушёл,
но статуса не получил — другая сторона сбросила стрим или оборвала соединение, — считается
отдельно, как `cut off`: цель или прокси могли его обработать, для записи это повод проверить
дубли. Вызов, прерванный нашей остановкой (Ctrl+C, SIGTERM), — `aborted` при любом коде: это не
отказ цели.

| Код | Статус пришёл по сети | Код поставил клиент, запрос ушёл | Код поставил клиент, запрос не ушёл |
|---|---|---|---|
| `INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `UNAUTHENTICATED`, `FAILED_PRECONDITION`, `OUT_OF_RANGE`, `UNIMPLEMENTED` | `request error` | `cut off` | `client error` |
| `RESOURCE_EXHAUSTED` | `overload`; «larger than max» от grpc-go — `request error` | `cut off`; ответ больше нашего лимита — `bad response` | `client error` |
| `UNAVAILABLE` | `overload` | `cut off`; поток, отвергнутый целью до обработки, — `overload` | `unreachable`; то же |
| `CANCELLED`, `UNKNOWN`, `INTERNAL`, `DATA_LOSS`, `ABORTED` | `failure`; OK без ответа от grpc-go — `bad response` | `cut off`; ответ не распаковался — `bad response` | `client error` |
| `DEADLINE_EXCEEDED` | тайм-аут | тайм-аут | тайм-аут, не отправлен |

Слишком большой запрос узнаётся по тексту ошибки grpc-go. Цель на другой реализации (Envoy, Java)
пишет его иначе, и такой отказ попадёт в `overload`, а не в `request error`.

`UNAVAILABLE` у отвергнутого потока — перевод grpc-go для RST_STREAM REFUSED_STREAM от цели: код
поставил клиент, а отказ прислала цель, поэтому он в строке «sent by the target». Такой поток цель
не обрабатывала (RFC 9113 §8.7).

Под отчётом упавшие вызовы разложены по кодам gRPC в две строки. «sent by the target» — статус
пришёл по сети, от цели или от прокси. «set by the client» — код поставил сам клиент: никто не
ответил, стрим сброшен, истёк наш дедлайн или клиент не принял ответ. `DEADLINE_EXCEEDED` от цели
обычно наш же дедлайн: он уходит цели в заголовке `grpc-timeout`. Категория говорит, чья это вина,
код — что искать в логах цели.

**Ожидания на стороне клиента.** В латенси входит всё, что вызов прождал у нас: опоздание
генератора, ожидание соединения, ожидание свободного стрима. Если без них p99 хоть одного метода
падает на 10 % и больше или часть вызовов так и не ушла, отчёт выносит вердикт и называет причину,
которая чаще других в хвосте p99, и печатает p99 без ожиданий — время, которое вызов провёл у цели.
Если причина — кончились стримы, ёмкость цели выше «лимит × соединения» не измерена. Если перед
вызовом ждали резолвер, в ожидание соединения попадают и интерсепторы вызывающего, поэтому p99 без
ожиданий может выйти немного заниженным. Неотправленные вызовы разбиты по причинам. Сдвиг меньше
10 % — не вердикт, а заметка с числом; если p99 — нижняя граница, сдвиг неизвестен, и заметки нет.

**Часы.** Инструмент меряет шаг часов хоста до и после прогона. Шаг заметен — печатается строка
`clock step 502us on this host: every latency and wait is +/- 502us`. На Linux шаг — десятки
наносекунд, строки нет.

### Паспорт прогона

Над отчётом стоит паспорт: на какой машине и с каким конфигом сделан прогон, чтобы два отчёта
можно было сравнить и не гадать, чем они отличаются. Он есть у прогона и у поиска точки отказа.

```text
machine: linux/amd64, 8 CPU, GOMAXPROCS 8, quota 4, go1.27.1; config sha256:3f9a1c0d2b7e
labels: commit=abc123, env=staging
```

- `quota` — лимит CPU контейнера (cgroup) как он задан; строки без него нет.
- Хеш — SHA-256 файла конфига как он лежит на диске, его покажет и `sha256sum load.yaml`; в тексте
  первые 12 цифр, в JSON все. Любая правка файла, даже комментария, меняет хеш. Хеш берётся до
  подстановки `${ENV}`: секреты в `metadata` пишите через `${ENV}`, а не значением в файле.
- Метки — `labels:` в конфиге и `-label ключ=значение` в командной строке (можно повторять; флаг
  перекрывает тот же ключ из конфига):

```sh
leettest -c load.yaml -label env=staging -label commit=abc123
```

Ключ — латиница, цифры и `_.-`, до 64 знаков; значение — строка до 256 байт, в YAML число берите
в кавычки (`build: "1.10"`). Нарушение — код `1` до старта. В JSON паспорт — поле `passport`, у
датасета рядом с `file` стоит `sha256`; все поля — в
[справочнике](docs/ru/reference.md#поля-json).

## Когда прогон недействителен

Отчёт есть, но числа не про нагрузку на цель (код 2), если:

- **упёрся в потолок `-max-in-flight`.** Таймауты и потолок сверяются до старта так, что зависшая
  цель в него не упирается; упор значит, что генератору не хватило процессора.
- **все измеренные вызовы метода — `request error`, `client error` или `bad response`.** Заметка
  называет метод, причину и что делать.
- **часы хоста грубее четверти p50** какого-либо метода, или шаг вырос за прогон до 1 мкс и выше
  (`clock_step`). Мерьте с Linux.
- **предел `pass` нельзя решить** (`thresholds_undecided`): мало наблюдений, генератор опоздал,
  вызовы ждали свободный поток, хвост из вызовов без ответа. Блок `Thresholds:` называет предел и
  причину.

## Пределы: прогон как проверка

Без `pass` дошедший до конца прогон возвращает `0`, как бы цель ни отвечала. Чтобы прогон сам
говорил «держит / не держит», задайте пределы под вызовом:

```yaml
app:
  target:
    ip: localhost
    port: 50051
  tls: false

load:
  warmup: 5s
  calls:
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      pass:
        p99: 200ms
        errors: 1%
```

```sh
leettest -c pass.yaml
echo $?
```

В конце отчёта появится блок: худший из вердиктов и строка на предел. Для здорового сервиса:

```
Thresholds: passed
  wallet.v1.WalletService/GetBalance  p99     <= 200ms  pass  21.2ms
  wallet.v1.WalletService/GetBalance  errors  <= 1%     pass  0.0% (0 of 44000)
```

Ключи: `p50`, `p90`, `p95`, `p99`, `p999` и `errors`; предел задержки требует `errors` рядом, а
`errors: 100%` снимает проверку отказов — тогда и латенси ничего не стоит. Предел поиска точки
отказа — `breakpoint.pass.held_rps`. Пропущенный предел даёт код `4`, предел, который нельзя решить
(мало наблюдений, генератор опоздал, хвост из вызовов без ответа), — код `2`. Все ключи, вердикты и
причины — в [справочнике](docs/ru/reference.md#пределы-pass); пример со всеми ключами —
[`examples/pass.yaml`](examples/pass.yaml).

## Коды выхода

Без `pass` дошедший до конца прогон возвращает `0`, как бы цель ни отвечала: **`0` не значит
«сервис здоров»**. С `pass` `0` значит, что каждый предел проверен и выдержан. Коды ранжированы:
недействительный прогон (`2`) важнее неполного (`3`); остановка, которая напечатала отчёт, всегда
`3`; законченный прогон, пропустивший предел, — `4`, а пределы не превращают недействительный или
остановленный прогон в `4`.

| Код | Что случилось |
|---|---|
| `0` | План выполнен, отчёт полный; с `pass` — все пределы выдержаны |
| `1` | Отчёт, который просили, не получен: прогон не состоялся (флаги, конфиг, подключение) или отчёт не записан в `-json-file`. Причина — в stderr |
| `2` | Прогон недействителен (см. выше) или предел `pass` нельзя решить. Отчёт есть, но числа не про нагрузку или не отвечают на вопрос предела |
| `3` | Прогон остановлен раньше плана. Отчёт есть и покрывает только то, что успело пройти |
| `4` | Законченный прогон пропустил предел `pass`. Отчёт есть, `outcome` в JSON — `complete` |
| `130` | Аварийный выход без отчёта после Ctrl+C |
| `143` | Аварийный выход без отчёта после SIGTERM |

Как работает остановка — в [справочнике](docs/ru/reference.md#остановка).

## JSON для скриптов и CI

С `-output json` в stdout идёт ровно один JSON-объект и перевод строки; всё остальное — в stderr,
так что stdout можно сразу отдать `jq`. Объект печатается только для прогона, который состоялся
(коды `0`, `2`, `3`, `4`); при `1`, `130` и `143` stdout пуст. Поле `outcome` — `complete`,
`invalid` или `incomplete` — совпадает с кодом выхода `0`, `2`, `3`; код `4` — это `complete`, а
какой предел пропущен, говорит поле `thresholds`. Единственное расхождение: если отчёт не удалось
записать в файл, код `1`, а в stdout остаётся объект прогона.

Текст в логе и JSON для следующего шага из одного прогона — `-json-file`:

```sh
leettest -c load.yaml -json-file report.json
```

В stdout всё как задано `-output` (по умолчанию текст), в `report.json` — тот же объект, что
печатает `-output json`. Файл создаётся до старта и не перезаписывается: если он уже есть или
каталога нет, код `1` и ни одного вызова к цели. Прогон без отчёта (например, `1` на подключении
или `130`) не оставляет файла. Если запись после прогона не удалась, stderr называет путь и
ошибку, а код — `1`.

Схема версионируется полем `schema_version`, сейчас `1`, и это контракт; текст на экране — нет,
разбирайте JSON, а не экран. Правила:

- новое поле добавляется без смены версии; переименование, удаление или смена типа поля
  повышают `schema_version`;
- набор значений перечислений (`outcome`, `unchecked[].reason`, коды в `failure_codes`) может
  расширяться без смены версии;
- потребитель обязан пропускать неизвестные поля и обрабатывать неизвестное значение
  перечисления, не падая.

Единица — в имени поля: `_us` — целые микросекунды, `_s` — целые секунды; частота `rps` —
единственное дробное число. Значение, которого прогон не дал, — `null`, а не `0`. Перцентиль —
объект `{"us": 1234, "ns": 1234567, "lower_bound": false}`: `ns` — значение гистограммы в целых
наносекундах, `us` — оно же, обрезанное до микросекунд; `pass:` и `leettest compare` судят по `ns`, а в
отчёте, записанном до этого поля, берёт `us` × 1000. При `lower_bound: true` это нижняя граница, а
не значение. Задержки — значения гистограммы с точностью 3 значащие цифры (погрешность до 0,1%),
счётчики точные. Время отсчитывается от `started_at` (RFC 3339, UTC) — начала расписания, прогрев
включён; `duration_us` тоже включает прогрев. `in_flight` в секунде — сколько вызовов было в
полёте на её конце. Коды в `failure_codes` — канонические имена (`UNAVAILABLE`). Сверка: итоги прогона —
сумма итогов методов, а по секундам метода `Σ begun` плюс `outside_timeline` — все его вызовы,
включая прогрев.

Решения — полями, а не текстом: `invalid_reasons` (`in_flight_cap`, `nothing_measured`,
`clock_step`), `methods[].invalid_reason` (`request_error`, `client_error`, `bad_response`, `mixed`
или `null`), `tail_wait_cause` (`generator`, `stream`, `connection` или `null`) и числа по причинам
в `client_waits`. `notes` и `unchecked[].error` — текст для человека, он меняется свободно, не
разбирайте его.

Тишина цели: `methods[].silent_from_s` — секунда, с которой цель не ответила ни на один
отправленный вызов, `methods[].silent_sent_rps` — сколько вызовов ушло за секунду до неё,
`methods[].silent_planned_rps_low` и `_high` — плановый темп стадий в ту же секунду. Без тишины все
`null`; плановый темп `null` и тогда, когда в ту секунду стадий уже не было. `planned_rps_low` и
`_high` — темп всего плана.

Текстовый отчёт печатается только в ASCII. Символы извне ASCII — в имени метода, в тексте ошибки
от цели — печатаются как `\uXXXX` (за пределами U+FFFF — парой суррогатов, как в JSON). `notes` в
JSON несут тот же экранированный текст.

### Поиск точки отказа

Секция `load.breakpoint` вместо `rps` и `duration` у вызова: LeetTest поднимает нагрузку ступенями
и называет, на какой ступени цель держалась и на какой сломалась. Вызов — ровно один, без `rps`,
`duration` и `load.warmup`.

```yaml
load:
  calls:
    - method: wallet.v1.WalletService/GetBalance
      timeout: 500ms
  breakpoint:
    from: 100         # первая ступень, rps
    to: 2000          # выше не идём
    factor: 1.25      # следующая ступень = прошлая × factor; или step: 100 — на столько rps больше
    settle: 5s        # начало ступени, не идущее в вердикт; меньше половины hold
    hold: 30s         # длина ступени
    p99_limit: 200ms  # необязательно; без него ступень ломается на p99 больше 3× лучшей выдержанной
    errors_limit: 1%  # необязательно; ступень ломается, если упало больше этой доли вызовов
```

Ступень ломается, если упало больше `errors_limit` вызовов (по умолчанию 1%; ровно столько ещё
выдерживается, `100%` — ошибки не ломают) или p99 перешёл порог. Вызов, не отправленный из-за
соединения, ломает ступень при любом `errors_limit`. Ошибки клиентской стороны (`request_error`,
`client_error`, `bad_response`) не доказывают, что сломалась цель: если лимит превышен только с
ними, поиск останавливается как `run_limit` с причиной `client_errors`, а не объявляет точку
отказа; `held_rps` остаётся. Сломанная ступень
повторяется после паузы и, кроме первой, после проб на первой ступени: цель должна вернуться к
прежнему p99. Ступень засчитывается выдержанной, только если генератор отправил запланированное — не
меньше 99,9% вызовов окна измерения. Иначе это предел прогона, а не цели. До первой ступени в
stderr — строка `breakpoint: up to N steps, at most T`: сколько ступеней и сколько поиск займёт в
худшем случае. Соединение одно на весь поиск; если цель его рвёт, ступень сломана, переподключения
нет.

Итог (`outcome` в JSON) — закрытый список: `broke` (держала X, сломалась на Y), `broke_at_first`
(сломалась уже на первой ступени — начните ниже), `held_all` (выдержала всё до `to`), `run_limit`
(кончился генератор, лимит соединения или `-max-in-flight`: о цели выше ничего не известно),
`stopped` (Ctrl+C), `invalid` (ступень оказалась недействительным прогоном). Причина (`why`) —
тоже закрытый список: `errors`, `p99_limit`, `p99_vs_base`, `connection`, `no_recovery`,
`generator`, `in_flight_cap`, `stream_limit`, `stream_wait`, `client_errors`, `clock_step`,
`request_errors` или `null`. Лимит ошибок — строка `breakpoint.errors_limit`. `held_rps` и `broke_rps` — `null`, где их нет. В режиме поиска JSON — другой объект:
`mode: "breakpoint"`, полей обычного прогона на верхнем уровне нет, каждый прогон со своим полным
отчётом лежит в `breakpoint.runs` (`kind`: `step`, `repeat`, `probe`; `planned_rps` и `sent_rps`).
Обычный прогон пишет `mode: "run"`.

Коды выхода: `0` для `broke`, `broke_at_first`, `held_all`, `run_limit` — это находки; `2` для
`invalid`; `3` для остановки одним Ctrl+C; `4` — поиск удержал меньше `breakpoint.pass.held_rps`.

### Сравнить два поиска

Два отчёта поиска, записанные `-json-file`, — до изменения и после. `leettest compare`
говорит, на сколько упала ёмкость (`held_rps`), и с `-max-capacity-drop` судит её.
На стенде из корня репозитория: поиск при ёмкости 270 rps (в терминале стенда), затем в другом
терминале — поиск и отчёт «до»:

```sh
go run ./test/stand/cmd/stand -capacity 270 -delay 20ms
```

```sh
leettest -c examples/breakpoint-step.yaml -json-file before.json
```

Остановите стенд (Ctrl+C), запустите его с ёмкостью 200 rps и снимите отчёт «после»:

```sh
go run ./test/stand/cmd/stand -capacity 200 -delay 20ms
```

```sh
leettest -c examples/breakpoint-step.yaml -json-file after.json
```

Сравните (стенд можно остановить):

```sh
leettest compare -max-capacity-drop 10% before.json after.json
```

```
base: before.json  Health  2026-10-19T19:25:28.941479Z
new:  after.json  Health  2026-10-19T19:26:46.1806268Z
capacity: 250 rps -> 200 rps, drop 20.0%, limit 10%: FAIL
```

Ёмкость упала с 250 до 200 rps, это 20% при пределе 10%, код выхода `4`. Время и стенд у вас будут
свои, числа — по ёмкости стенда.

Отчёты сравнимы, только если совпадают цель, метод, версия LeetTest, паспорт прогона (кроме
меток) и набор данных; иначе строки `differs:` называют поле, а вердикт — `unknown`. Если поиск
кончился раньше отказа, ёмкость — нижняя граница (`>= N rps`); если цель сломалась уже на первой
ступени — верхняя (`below N rps`). Тогда падение печатается границей (`drop <= 33.4%`), а предел
решается, только если граница его решает. Без `-max-capacity-drop` ничего не судится. Коды выхода:
`0` — в пределе или предела нет, `1` — отчёт не прочитан, `2` — отчёты несравнимы или предел нельзя
решить, `4` — ёмкость упала больше предела.

### Сравнить два прогона

Те же команды читают и отчёты обычного прогона (`-json-file`): `-max-p99-rise` судит
рост p99 каждого метода в процентах от p99 «до», `-max-errors-rise` — рост доли неудачных вызовов в
процентных пунктах. Без предела строка печатается, но не судится. Отчёт поиска и отчёт прогона в
одной команде — код `1`. На стенде из корня репозитория: прогон при задержке 20 ms, затем при 30 ms:

```sh
go run ./test/stand/cmd/stand -delay 20ms -life 60s
```

```sh
leettest -c examples/stand.yaml -json-file before.json
```

Стенд завершится сам через минуту; запустите его с задержкой 30 ms и снимите отчёт «после»:

```sh
go run ./test/stand/cmd/stand -delay 30ms -life 60s
```

```sh
leettest -c examples/stand.yaml -json-file after.json
```

Сравните (стенд можно остановить):

```sh
leettest compare -max-p99-rise 20% before.json after.json
```

```
base: before.json  Health  2026-10-20T12:40:09.5222467Z
new:  after.json  Health  2026-10-20T12:40:42.469917Z
grpc.health.v1.Health/Check: p99 21.2ms -> 31.3ms, rise 47.3%, limit 20%: FAIL
grpc.health.v1.Health/Check: errors 0.0% -> 0.0%, no change
```

p99 вырос с 21.2 до 31.3 ms, это 47.3% при пределе 20%, код выхода `4`. Время и задержки у вас
будут свои.

Проверка бывает `unknown` (код `2`), если отчёты несравнимы (как выше), прогон недействителен или
неполон, замеров слишком мало, p99 упёрся в таймаут (значит, он больше напечатанного, `>=`) или
ошибки самого клиента не дают решить, виноват ли сервис. Методы, которых нет в обоих отчётах, не
сравниваются. Коды выхода те же, что у поисков.

Для скрипта и CI тот же результат — одним JSON-объектом: `-output json` печатает в
stdout только его, коды выхода и stderr те же, что у текста; при коде `1` stdout пуст.

```sh
leettest compare -max-p99-rise 20% -output json before.json after.json
```

В объекте `verdict` — худший вердикт проверок с пределом (`null`, если пределов нет), а в
`checks` — каждая проверка с числами обоих отчётов; у `unknown` причина в `reason` — значение из
закрытого списка:

```json
{"schema_version":1,"mode":"compare","compared_mode":"run","comparable":true,"differences":[],"verdict":"fail","checks":[{"method":"/grpc.health.v1.Health/Check","key":"p99","base_p99":{"us":21381,"ns":21381472,"lower_bound":false},"new_p99":{"us":31358,"ns":31358109,"lower_bound":false},"limit_percent":"20%","verdict":"fail","reason":null,"why":null}]}
```

Показаны не все поля: пустые у этой проверки (`base_capacity` и другие `null`) и описание
отчётов (`base`, `new`) опущены. Процента роста в объекте нет — скрипт считает его из `us`. Каждое
поле описано в [справочнике, «JSON сравнения»](docs/ru/reference.md#json-сравнения).

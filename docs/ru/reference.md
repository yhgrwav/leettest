## Конфиг

```yaml
name: wallet                     # необязательно
app:
  target:
    ip: localhost
    port: 50051
  tls: false

load:
  warmup: 5s
  calls:
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      timeout: 2s
```

| Поле | Что делает |
|---|---|
| `name` | Необязательно. Как назвать прогон в заголовке. Не указано — имя сервиса, если все методы из одного, иначе имя файла конфига |
| `app.target` | Адрес сервиса: `ip` и `port` |
| `app.tls` | TLS. Не указан — включён. `false` — подключение без шифрования |
| `app.ca` | PEM-файл с сертификатами, которым проверять сервис вместо системных. Нужен TLS |
| `app.cert`, `app.key` | Клиентский сертификат и его ключ в PEM, для сервиса с mTLS. Только вместе, нужен TLS |
| `app.server_name` | Имя, по которому проверять сертификат сервиса, если он не называет адрес из `target`. Нужен TLS |
| `app.metadata` | Заголовки каждого вызова: `authorization`, `x-api-key` и т. п. `${ИМЯ}` берётся из переменной окружения |
| `app.max_response_size` | Самый большой ответ, который примет вызов: `16MiB`, `512KB`. Единица обязательна (`MB` = 10⁶ байт, `MiB` = 2²⁰), меньше 2 GiB. Не указан — 4 MiB, как у gRPC. Ответ больше — `bad response`. Вызов в полёте держит в памяти до двух лимитов: по умолчанию до 8 MiB на каждый |
| `app.connections` | Сколько соединений открыть к цели, целое от 1 до 256. Не указано — 1. Вызовы идут по соединениям по кругу, отчёт печатает блок `Connections:` — строку на соединение — не выпущено |
| `load.warmup` | Первые N секунд не попадают в percentiles и в `sent`: холодные кеши их портят. Вызовы прогрева уходят к цели, отчёт печатает их строкой `warm-up N sent (M failed), excluded from stats` — `sent` плюс она равны всем вызовам, которые генератор попытался отправить. Цель получила их все, кроме посчитанных как unreachable и client error; `cut off` и вызовы с тайм-аутом могли дойти до неё не полностью: цель, которая не открывает окно HTTP/2 (flow control), получает только заголовки, и её счётчики могут вызов не увидеть. Входит в `duration`, короче любого вызова |
| `load.calls[].method` | Полное имя метода: `пакет.Сервис/Метод` |
| `load.calls[].rps` | Запросов в секунду для этого метода |
| `load.calls[].duration` | Сколько его нагружать: `30s`, `5m`, `1h` |
| `load.calls[].timeout` | Сколько ждать ответа. Не указан — `2s`. Ноль не отключает, а даёт ошибку |
| `load.calls[].data` | Тело запроса, см. [ниже](#тело-запроса). Не указано — пустое сообщение |
| `load.calls[].dataset` | Файл с телами запросов вместо `data`, см. [ниже](#каждый-раз-другой-запрос-dataset). Вместе с `data` нельзя — не выпущено |

Конфиг читается строго: опечатка в имени поля — ошибка с номером строки, неверное значение —
ошибка с номером вызова и его методом, а не прогон с пустой нагрузкой. `rps` — целое число:
`10.5` отклоняется, а не округляется молча до десяти. `warmup` обязан быть короче каждого вызова,
иначе от вызова не осталось бы ни одного измеренного запроса.

**Таймаут и потолок запросов в полёте.** Если сервис завис, каждый метод держит в полёте
`rps × timeout` запросов, пока не сработает таймаут, плюс запас: один запрос на границе окна и
`rps × 100 мс` на то, что генератор освобождает место чуть позже дедлайна. Сумма по методам не
должна превышать `-max-in-flight` (по умолчанию 5000). Это проверяется до старта, ошибка называет
оба выхода: какой таймаут влезет и какой нужен потолок. Поэтому зависший сервис в потолок не
упирается: прогон доходит до конца, а отчёт говорит, сколько вызовов не получили ответа за
таймаут и после какого отправленного вызова цель больше не отвечала. Если потолок всё же кончился,
место держали дольше дедлайна больше чем на 100 мс — это генератор (не хватило процессора) или
отправитель, и отчёт объявляет прогон недействительным. Рядом печатается, сколько слотов в момент
упора держались после своего дедлайна.

## Доступ к сервису

```yaml
app:
  target:
    ip: 10.0.3.17
    port: 443
  ca: certs/ca.pem            # пути — относительно файла конфига
  cert: certs/client.pem
  key: certs/client.key
  server_name: payments.internal
  metadata:
    authorization: Bearer ${PAYMENTS_TOKEN}
    x-api-key: ${PAYMENTS_KEY}
```

**Секреты.** `${ИМЯ}` подставляется из переменной окружения, в том числе внутри значения:
`Bearer ${TOKEN}`. Переменная не задана или задана пустой — ошибка до старта с её именем. Иначе
ушёл бы `Bearer ` без токена, и прогон показал бы 100% отказов как вину цели. Чтобы написать
`${` буквально, удвойте доллар: `$${`. Одиночный `$` остаётся как есть. Подстановка работает
только в `app.metadata`: в `data`, `target` и остальных полях `${ИМЯ}` уходит как написано.
Флага для заголовков нет, поэтому токен не попадает ни в `ps`, ни в историю shell. Значения
заголовков инструмент не печатает нигде: ни в отчёте, ни в ходе прогона, ни в ошибках.

**Заголовки.** Имена приводятся к нижнему регистру, как их и передаёт HTTP/2. Ошибка конфига до
старта: ключ с `grpc-` (его резервирует gRPC), псевдозаголовки вроде `:path`, ключ с `-bin`
(бинарные заголовки пока не поддерживаются), значение вне печатаемого ASCII. Те же заголовки и
сертификат уходят в проверку методов перед стартом. Если цель на ней ответила `Unauthenticated`,
а заголовки заданы, прогон не начнётся: «target rejected credentials». `PermissionDenied` прогон
не останавливает: токен принят и может работать для вызовов, не пуская к reflection; методы
помечаются непроверенными. `Unauthenticated` без заголовков тоже не останавливает, а в заметке
сказано: «target requires credentials; app.metadata is not set».

**Сертификаты.** `ca` заменяет системные корни, а не добавляется к ним. Проверка сертификата
цели не отключается ничем. `server_name` меняет только имя, с которым сверяется сертификат и
которое уходит в SNI; `:authority` остаётся адресом из `target`. Зашифрованный паролем ключ не
поддерживается: его нужно расшифровать заранее.

**Соединения.** По умолчанию генератор держит одно соединение к одному адресу. Если DNS отдаёт
несколько адресов или цель стоит за L4-балансировщиком, нагружается только один бэкенд, и отчёт
этого не покажет. `app.connections: N` (не выпущено) открывает N соединений. Имя, которое DNS
раскрывает в M адресов, разрешается один раз перед стартом, и соединение i идёт на адрес i mod M:
три соединения на два адреса — два и одно. Адрес, который не обслуживает цель (`localhost` в
`::1`, сервер слушает только `127.0.0.1`), останавливает старт и назван в ошибке: укажите его IP.
Блок отчёта показывает по соединению адрес, вызовы, долю отказов и p99, так что мёртвый или
медленный бэкенд за именем не усредняется. Повторов вызовов нет.
Service config от сервиса игнорируется: повторы и политика балансировки из него не применяются.
Боевой клиент, который их применяет, увидит другие категории и p99.

**Ошибки до старта.** Всё, что можно узнать до прогона, — код выхода 1 и ни одного вызова к
цели: файл не найден или не PEM, сертификат не подходит к ключу, сертификат цели просрочен или
не называет адрес (подсказка — `server_name`), цель закрыла соединение сразу после
рукопожатия (не приняла клиентский сертификат), TLS включён, а цель без него, или наоборот.

## Тело запроса

```yaml
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      data:
        wallet_id: "w-123"
        currency: USD                         # enum — по имени
        filter:
          since: "2026-01-01T00:00:00Z"       # google.protobuf.Timestamp
```

`data` — обычный YAML в форме сообщения. Схему инструмент берёт у сервиса через server
reflection; `.proto` не нужен. Тело собирается один раз до старта, и любая ошибка в нём —
неизвестное поле, не тот тип, несуществующий метод — видна сразу, с именем метода и поля, до
первого запроса. Нет `data` — уходит пустое сообщение, и reflection такому методу не нужен.

**Одно тело на метод.** Все вызовы метода уходят с одним и тем же `data`. Для записи с ключом
идемпотентности это значит, что первый вызов создаёт запись, а все следующие идут по пути повтора:
цель отдаёт уже сохранённый ответ. Меряется этот путь, а не создание записи.

Правила значений — стандартные правила JSON для protobuf (`protojson`):

- имя поля — как в `.proto` (`wallet_id`) или в JSON-форме (`walletId`);
- enum — по имени; `Timestamp`, `Duration` — строкой в их формате;
- `int64` и `uint64` доходят точно, в том числе больше 2^53 (snowflake-ID, суммы в минимальных
  единицах): число нигде не проходит через float;
- число с ведущим нулём (`0123`, `007`) — ошибка конфига: YAML прочитал бы его как восьмеричное.
  Нужен ноль — пишите строкой, `"0123"`;
- **`bytes` — строкой в base64.** `signature: abcd` — это не четыре байта `abcd`, а три других
  байта: `abcd` сам по себе валидный base64, и ошибки не будет. Четыре байта `abcd` пишутся как
  `signature: YWJjZA==`.

**Проверка методов.** Каждый метод из конфига проверяется у сервиса до старта: опечатка в имени
или метод, которого там нет, — ошибка до первого запроса, а не прогон, где все вызовы падают с
`Unimplemented`. Если reflection на сервисе выключен, метод с `data` не запустится — ошибка скажет
это прямо. Метод без `data` работает и без reflection: проверить его нечем, и об этом печатается
предупреждение — перед прогоном в stderr и ещё раз строкой в отчёте. В предупреждении сказано,
почему проверить не удалось: reflection выключен, ответил отказом или не ответил вовсе.

## Каждый раз другой запрос: dataset

```yaml
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      dataset: wallets.jsonl
```

```
{"wallet_id": "w-1", "currency": "USD"}
{"wallet_id": "w-2", "currency": "EUR"}
```

`dataset` — файл с телами запросов, по одному JSON на строку, в той же форме, что и `data`.
Относительный путь отсчитывается от каталога файла конфига. Первый запрос уходит с первой строкой,
второй — со второй, после последней строки — снова с первой. Пустые строки пропускаются. Файл
читается, и каждая строка проверяется по сообщению метода до старта — по правилам `data` и через
reflection; ошибка называет строку, `wallets.jsonl:3`, и никогда не печатает то, что в ней
написано. Файл без запросов — ошибка.

Под строкой метода отчёт говорит, сколько файла использовано:
`data: 3 of 3 requests from wallets.jsonl, each used up to 5 times`. Это сколько раз запрос отдан
отправителю, а не что увидела цель: запрос, который в файле стоит дважды, уйдёт дважды, а вызов,
не дошедший до цели, тоже посчитан. В поиске точки разрыва каждый шаг продолжает с того места, где
кончился прошлый, а строка считает весь поиск.

## Флаги

| Флаг | Что делает |
|---|---|
| `-c` | Путь к конфигу |
| `-output` | Формат отчёта в stdout: `text` (по умолчанию) или `json` для скриптов и CI |
| `-connect-timeout` | Сколько ждать сервис, который принял соединение, но молчит. По умолчанию `10s`. Отказ в соединении и неверный адрес не ждут |
| `-max-in-flight` | Потолок запросов, ждущих ответа. По умолчанию `5000` |
| `-plain` | Без живого экрана: строка прогресса раз в секунду в stderr, как без терминала, и без диалога первого запуска. Отчёт и коды выхода те же — не выпущено |
| `-fake` | Нагружать встроенную заглушку вместо сервиса из конфига — посмотреть на инструмент без сервиса. Отчёт помечен `fake target` |
| `-fake-delay`, `-fake-jitter`, `-fake-fail-ratio` | Поведение заглушки. Только вместе с `-fake` |
| `-version` | Напечатать версию и выйти. Собранное из исходников печатает коммит |

## Остановка

`q` в полноэкранном виде, Ctrl+C без него:

- первое нажатие — новые запросы не уходят, запросы в полёте дорабатывают до своего таймаута и
  попадают в отчёт как обычно;
- второе — запросы в полёте обрываются и считаются отдельно как оборванные (`aborted`): не отказ
  сервиса, а нижняя граница времени; отчёт печатается;
- третье — выход сразу, без отчёта.

В полноэкранном виде верхняя строка ведёт по этим ступеням.

SIGTERM (`docker stop`, Kubernetes, отмена джоба в CI) сразу обрывает запросы в полёте и
печатает отчёт, минуя мягкую остановку: оркестратор через несколько секунд убивает процесс, и
отчёт должен успеть выйти. Если обрыв уже идёт, SIGTERM его не прерывает.

Остановленный прогон помечается в отчёте как неполный (код 3): числа в нём честные, но покрывают
меньше, чем было запланировано.

## Поля JSON

Правила контракта — версия схемы, единицы, `null` вместо `0`, неизвестные поля — в
[README](../../README.md#json-для-скриптов-и-ci). Здесь — каждое поле `schema_version` 1. Тип с `?`
может быть `null`. Счётчики прогрева не входят ни в какие другие счётчики; `sent` и все его доли
— только измеренные вызовы. В первой колонке — полный путь поля.

**Перцентиль** — объект; `null` — нет ни одного наблюдения. `<перцентиль>` — любое поле с типом
«перцентиль?» ниже.

| Поле | Тип | Что значит |
|---|---|---|
| `<перцентиль>.us` | int | Значение, целые микросекунды |
| `<перцентиль>.lower_bound` | bool | `true` — это нижняя граница, а не значение ([README](../../README.md#как-читать-отчёт)) |

### Прогон

| Поле | Тип | Что значит |
|---|---|---|
| `schema_version` | int | Версия схемы, сейчас `1` |
| `mode` | string | `run` у обычного прогона, `breakpoint` у поиска точки отказа — не выпущено |
| `leettest_version` | string | Версия инструмента; собранное из исходников — коммит |
| `target` | string | Адрес цели из конфига, `fake target` при `-fake` |
| `outcome` | string | `complete`, `invalid`, `incomplete` — совпадает с кодом выхода `0`, `2`, `3` |
| `invalid_reasons` | []string | Почему прогон недействителен: `in_flight_cap`, `nothing_measured`, `clock_step`. Пустой — действителен |
| `tail_wait_cause` | string? | Ожидание на стороне клиента, которое задало хвост: `generator`, `stream`, `connection`; `null` — вердикта нет |
| `clock_step_ns` | int | Шаг часов хоста, нс: каждая задержка и ожидание ± он |
| `started_at` | string | Начало расписания, RFC 3339 UTC, прогрев включён. От него отсчитываются все `_us` и `_s` |
| `duration_us` | int | Сколько прогон шёл, прогрев включён |
| `planned_us` | int | Сколько он должен был идти |
| `warmup_us` | int | Длина прогрева |
| `sent` | int | Измеренные вызовы, кроме `not_sent`. `unreachable` и `aborted` входят |
| `failed` | int | Из `sent` — все неуспешные, кроме `aborted` |
| `aborted` | int | Оборваны нашей остановкой |
| `not_sent` | int | Таймаут истёк до отправки: в `sent` и `failed` не входят |
| `not_sent_generator`, `not_sent_stream`, `not_sent_connection` | int | `not_sent` по причине: опоздал генератор, не было свободного стрима, не было готового соединения. В сумме — `not_sent` |
| `warmup_sent`, `warmup_failed`, `warmup_not_sent` | int | То же для вызовов, запланированных на прогрев |
| `cap_hit` | object? | Упор в `-max-in-flight`; `null` — упора не было |
| `cap_hit.at_us` | int | Когда |
| `cap_hit.unsent` | int | Сколько вызовов потолок не пустил |
| `cap_hit.over_deadline` | int | Сколько вызовов в полёте в тот момент держали слот после своего дедлайна |
| `start_lag` | object | Опоздание старта вызовов против расписания |
| `start_lag.p99` | перцентиль? | p99 опоздания |
| `start_lag.max` | перцентиль? | Максимум, всегда точный; `null` без вызовов |
| `connections` | object? | Соединения; `null`, если отправитель о них не сообщает |
| `connections.open` | int | Сколько соединений несли вызовы одновременно |
| `connections.reconnects` | int | Успешные рукопожатия после первого |
| `connections.first_limit`, `connections.last_limit` | int? | `MAX_CONCURRENT_STREAMS` на первом и последнем рукопожатии; `null` — цель не объявила (`0` — объявила ноль). При нескольких соединениях всегда `null`: лимиты у каждого свои |
| `connections.limit_changes` | int | Сколько рукопожатий объявили лимит, отличный от прежнего |
| `connections.resolved` | []string? | Адреса, которым соответствует цель, в порядке резолвера: все, даже если соединений меньше. IP-адрес — он сам; `null` при одном соединении — не выпущено |
| `connections.in_flight_limit` | int? | Сколько вызовов цель позволяет держать в полёте: лимит единственного соединения или сумма лимитов всех; `null`, пока хоть одно соединение лимит не объявило — не выпущено |
| `connections.per_connection` | []object? | По объекту на соединение, в порядке номеров блока отчёта; `null` при одном соединении — не выпущено |
| `connections.per_connection[].address` | string | Адрес соединения — не выпущено |
| `connections.per_connection[].calls` | int | Вызовы, назначенные соединению, отправленные и нет, без прогрева — не выпущено |

| `client_waits` | object | Вызовы, ждавшие на стороне клиента дольше порога, по причинам ([README](../../README.md#как-читать-отчёт)) |

| `methods` | []object | Методы, см. ниже |

| `unchecked[].reason` | string | `reflection_off` или `reflection_failed` |
| `unchecked[].error` | string | Текст для человека, меняется вместе с grpc-go |
| `notes` | []string | Заметки отчёта, текст для человека в ASCII; не разбирать |

### Метод: `methods[]`

`<категория>` — каждая из четырёх категорий, у которых в JSON есть свой объект с временем ответа:
`request_error`, `overload`, `failure`, `bad_response` ([категории](../../README.md#как-читать-отчёт)).
Остальные — просто счётчики.

| Поле | Тип | Что значит |
|---|---|---|
| `methods[].method` | string | Полное имя метода |
| `methods[].invalid_reason` | string? | Метод ничего не измерил про нагрузку: `request_error`, `client_error`, `bad_response`, `mixed`; `null` — измерил |
| `methods[].sent`, `methods[].failed`, `methods[].aborted`, `methods[].not_sent`, `methods[].not_sent_generator`, `methods[].not_sent_stream`, `methods[].not_sent_connection`, `methods[].warmup_sent`, `methods[].warmup_failed`, `methods[].warmup_not_sent` | int | Доля метода в одноимённых полях прогона |
| `methods[].rps` | float? | `sent/s`: отправленные, делённые на время отправки; `null` — ни одного вызова |
| `methods[].timeout_us` | int | Таймаут метода |
| `methods[].planned_rps_low`, `methods[].planned_rps_high` | int | Наименьший и наибольший плановый темп всего плана |
| `methods[].latency` | object | Задержка успешных вызовов, с таймаутами и оборванными как нижними границами |
| `methods[].latency.min`, `methods[].latency.p50`, `methods[].latency.p90`, `methods[].latency.p95`, `methods[].latency.p99`, `methods[].latency.max` | перцентиль? | Минимум, перцентили, максимум |
| `methods[].p99_without_client_waits` | перцентиль? | p99 тех же вызовов без ожиданий на стороне клиента; может выйти немного заниженным |
| `methods[].observations` | int | Наблюдений за перцентилями `latency` |
| `methods[].censored` | int | Из них известна только нижняя граница |
| `methods[].invalid_latencies` | int | Отброшены как невозможные (отрицательная задержка) — признак ошибки в коде, а не в цели |
| `methods[].timed_out` | int | Ушли и не получили ответа за таймаут |
| `methods[].timed_out_after_wait` | int | Из `timed_out` — ушли, когда от таймаута оставалось меньше половины |
| `methods[].cut_off` | int | Ушли и не получили статуса |
| `methods[].unreachable` | int | Не дошли до цели |
| `methods[].unclassified` | int | Отправитель не дал категорию — дефект отправителя, не наблюдение о цели |
| `methods[].outside_timeline` | int | Не попали в `seconds`: момент вызова не лёг на шкалу |
| `methods[].<категория>` | object | Ответы этой категории |
| `methods[].<категория>.count` | int | Сколько вызовов в ней |
| `methods[].<категория>.p50`, `methods[].<категория>.p90`, `methods[].<категория>.p95`, `methods[].<категория>.p99`, `methods[].<категория>.max` | перцентиль? | Её время ответа |

| `methods[].failure_codes` | []object | Упавшие вызовы по кодам gRPC |

| `methods[].failure_codes[].count` | int | Сколько |

| `methods[].silent_from_s` | int? | Секунда, с которой цель не ответила ни на один отправленный вызов; `null` — тишины нет |
| `methods[].silent_sent_rps` | int? | Сколько вызовов ушло за секунду до неё (за первую, если тишина с начала) |
| `methods[].silent_planned_rps_low`, `methods[].silent_planned_rps_high` | int? | Плановый темп стадий в ту же секунду; `null` и тогда, когда стадий в ней не было |

### Секунда: `methods[].seconds[]`

Шкала покрывает весь прогон, прогрев включён, до последней секунды, где что-то произошло. В
отличие от итогов в ней каждый вызов. Сверка: `Σ begun` + `outside_timeline` — все вызовы метода.

| Поле | Тип | Что значит |
|---|---|---|
| `methods[].seconds[].warmup` | bool | Секунда в прогреве |
| `methods[].seconds[].begun` | int | Вызовы, начатые в эту секунду |
| `methods[].seconds[].succeeded`, `methods[].seconds[].overload`, `methods[].seconds[].failure`, `methods[].seconds[].client_error`, `methods[].seconds[].bad_response`, `methods[].seconds[].request_error`, `methods[].seconds[].timed_out`, `methods[].seconds[].unreachable`, `methods[].seconds[].cut_off`, `methods[].seconds[].aborted`, `methods[].seconds[].unclassified` | int | Вызовы, завершившиеся в эту секунду, по категориям |
| `methods[].seconds[].not_sent_generator`, `methods[].seconds[].not_sent_stream`, `methods[].seconds[].not_sent_connection` | int | Таймауты до отправки, завершившиеся в эту секунду, по причинам |
| `methods[].seconds[].in_flight` | int | Вызовов в полёте на конце секунды |
| `methods[].seconds[].lag_calls`, `methods[].seconds[].lag_sum_us`, `methods[].seconds[].lag_max_us` | int | По вызовам, запланированным на эту секунду: сколько, сумма и максимум опоздания старта |
| `methods[].seconds[].observed_calls` | int | Из них успешных |
| `methods[].seconds[].observed_lag_sum_us`, `methods[].seconds[].transport_wait_sum_us`, `methods[].seconds[].service_time_sum_us` | int | По успешным: сумма опоздания старта, ожидания до отправки (соединение и стрим), времени от отправки до ответа. В сумме — их задержки |

### Поиск точки отказа: `mode: "breakpoint"`

Поиск пишет другой объект: поля `schema_version`, `leettest_version`, `target`, `started_at` — как у
прогона выше, полей обычного прогона на верхнем уровне нет. Каждый прогон лежит в `breakpoint.runs`
со своим полным отчётом ([поиск](../../README.md#поиск-точки-отказа)).

| Поле | Тип | Что значит |
|---|---|---|
| `method` | string | Метод, который нагружал поиск — не выпущено |
| `breakpoint` | object | Итог поиска — не выпущено |
| `breakpoint.outcome` | string | Закрытый список: `broke`, `broke_at_first`, `held_all`, `run_limit`, `stopped`, `invalid` — не выпущено |
| `breakpoint.held_rps` | int? | Наибольший темп, который цель выдержала; `null` — выдержавшего нет — не выпущено |
| `breakpoint.broke_rps` | int? | Наименьший темп, на котором цель сломалась или упёрся прогон; `null` — не ломалась — не выпущено |
| `breakpoint.why` | string? | Причина прогона, закончившего поиск, из закрытого списка: `errors`, `p99_limit`, `p99_vs_base`, `connection`, `no_recovery`, `generator`, `in_flight_cap`, `stream_limit`, `stream_wait`, `clock_step`, `request_errors`; `null` — причины нет — не выпущено |
| `breakpoint.notes` | []string | Заметки поиска, текст для человека в ASCII; не разбирать — не выпущено |
| `breakpoint.runs` | []object | Все прогоны по порядку — не выпущено |
| `breakpoint.runs[].kind` | string | `step`, `repeat` или `probe` — не выпущено |
| `breakpoint.runs[].planned_rps` | int | Плановый темп прогона — не выпущено |
| `breakpoint.runs[].sent_rps` | int | Темп, с которым вызовы реально ушли: держится только то, что отправлено — не выпущено |
| `breakpoint.runs[].broken` | bool | `true` — прогон сломал цель — не выпущено |
| `breakpoint.runs[].recovered` | bool? | У `probe`: цель вернулась к p99 в пределах 1,5 от исходного; у `step` и `repeat` — `null` — не выпущено |
| `breakpoint.runs[].why` | string? | Причина прогона, тот же закрытый список, что у `breakpoint.why`; `null` — причины нет — не выпущено |
| `breakpoint.runs[].report` | object | Полный отчёт этого прогона, тот же объект, что JSON обычного прогона (поля выше) — не выпущено |

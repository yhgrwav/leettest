## Конфиг

```yaml
name: wallet                     # необязательно
app:
  target:
    ip: localhost
    port: 50051
  tls: false

load:
  warmup: 5s
  calls:
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      timeout: 2s
```

| Поле | Что делает |
|---|---|
| `name` | Необязательно. Как назвать прогон в заголовке. Не указано — имя сервиса, если все методы из одного, иначе имя файла конфига |
| `labels` | Необязательно. Пары `ключ: "значение"`, которые печатает паспорт отчёта, чтобы различать прогоны (`env: staging`, `commit: abc123`). Ключ — от 1 до 64 символов `A-Za-z0-9_.-`; значение — строка YAML до 256 байт, число берите в кавычки (`"1.10"`). `-label` добавляет пару или заменяет пару конфига |
| `app.target` | Адрес сервиса: `ip` и `port` |
| `app.tls` | TLS. Не указан — включён. `false` — подключение без шифрования |
| `app.ca` | PEM-файл с сертификатами, которым проверять сервис вместо системных. Нужен TLS |
| `app.cert`, `app.key` | Клиентский сертификат и его ключ в PEM, для сервиса с mTLS. Только вместе, нужен TLS |
| `app.server_name` | Имя, по которому проверять сертификат сервиса, если он не называет адрес из `target`. Нужен TLS |
| `app.metadata` | Заголовки каждого вызова: `authorization`, `x-api-key` и т. п. `${ИМЯ}` берётся из переменной окружения |
| `app.max_response_size` | Самый большой ответ, который примет вызов: `16MiB`, `512KB`. Единица обязательна (`MB` = 10⁶ байт, `MiB` = 2²⁰), меньше 2 GiB. Не указан — 4 MiB, как у gRPC. Ответ больше — `bad response`. Вызов в полёте держит в памяти до двух лимитов: по умолчанию до 8 MiB на каждый |
| `app.connections` | Сколько соединений открыть к цели, целое от 1 до 256. Не указано — 1. Вызовы идут по соединениям по кругу, отчёт печатает блок `Connections:` — строку на соединение |
| `app.compression` | Сжимать тела запросов: `gzip`. Не указано — без сжатия. Отчёт печатает под методом `bytes: <raw> -> <wire> per call` |
| `app.proto.files` | Файлы `.proto`, из которых брать сервисы, для сервиса без reflection. Пути — от каталога файла конфига. Каждый файл должен лежать внутри одного из `import_paths` |
| `app.proto.import_paths` | Где искать файлы и их импорты, как `protoc -I`. Пути — от каталога файла конфига. Не указано — этот каталог. Стандартным типам (`google/protobuf/…`) путь не нужен |
| `app.protoset` | Файл набора дескрипторов вместо файлов `.proto`, собранный `protoc --include_imports --descriptor_set_out=FILE`. Путь — от каталога файла конфига. Не вместе с `app.proto`; нет ни того, ни другого — методы берутся через reflection |
| `load.warmup` | Первые N секунд не попадают в percentiles и в `sent`: холодные кеши их портят. Вызовы прогрева уходят к цели, отчёт печатает их строкой `warm-up N sent (M failed), excluded from stats` — `sent` плюс она равны всем вызовам, которые генератор попытался отправить. Цель получила их все, кроме посчитанных как unreachable и client error; `cut off` и вызовы с тайм-аутом могли дойти до неё не полностью: цель, которая не открывает окно HTTP/2 (flow control), получает только заголовки, и её счётчики могут вызов не увидеть. Входит в `duration`, короче любого вызова |
| `load.ramp` | Поднять каждый вызов с 0 до его `rps` линейно за это время, перед тем как начнётся его `duration`: прогон идёт `ramp` + `duration`, а `duration` значит то же, что раньше (время на `rps`). Не указан или `0s` — разгона нет. Вызовы разгона не попадают в percentiles и в `sent`, как и прогрева, который начинается, когда разгон кончился; отчёт печатает оба одной строкой `ramp and warm-up N sent, excluded from stats`. Пределы `pass` и доля ошибок считаются только по удержанию: цель, которая падала на разгоне и выправилась, пройдёт, и увидеть это можно только по этой строке. Разгон начинается с одного вызова в момент 0. Не вместе с `load.breakpoint`. (не выпущено) |
| `load.calls[].method` | Полное имя метода: `пакет.Сервис/Метод` |
| `load.calls[].rps` | Запросов в секунду для этого метода |
| `load.calls[].duration` | Сколько его нагружать: `30s`, `5m`, `1h` |
| `load.calls[].timeout` | Сколько ждать ответа. Не указан — `2s`. Ноль не отключает, а даёт ошибку |
| `load.calls[].data` | Тело запроса, см. [ниже](#тело-запроса). Не указано — пустое сообщение |
| `load.calls[].dataset` | Файл с телами запросов вместо `data`, см. [ниже](#каждый-раз-другой-запрос-dataset). Вместе с `data` нельзя |
| `load.calls[].dataset_order` | `file` (не указан) или `random`: порядок запросов из файла. Нужен `dataset` |
| `load.calls[].dataset_seed` | Целое от 0 до 9007199254740991, фиксирует случайный порядок. Нужен `dataset_order: random`. Не указан — выбирается сам и печатается в отчёте |
| `load.calls[].dataset_reuse` | `true` (не указан) или `false`: при `false` ни одна запись не уходит дважды за весь процесс. Нужен `dataset` |
| `load.calls[].pass` | Пределы, по которым прогон проходит или нет: `p50`, `p90`, `p95`, `p99`, `p999`, `errors`, см. [ниже](#пределы-pass). Не указано — пределов нет |
| `load.breakpoint.pass` | Предел поиска точки отказа: `held_rps`, см. [ниже](#пределы-pass). Не указано — предела нет |
| `load.breakpoint.errors_limit` | Процент вида `1%` или `0.5%`, до трёх знаков после точки, не больше `100%`. Ступень поиска ломается, если упало больше этой доли вызовов; ровно столько выдерживается. Не указано — `1%` |

Конфиг читается строго: опечатка в имени поля — ошибка с номером строки, неверное значение —
ошибка с номером вызова и его методом, а не прогон с пустой нагрузкой. `rps` — целое число:
`10.5` отклоняется, а не округляется молча до десяти. `warmup` обязан быть короче каждого вызова,
иначе от вызова не осталось бы ни одного измеренного запроса.

**Таймаут и потолок запросов в полёте.** Если сервис завис, каждый метод держит в полёте
`rps × timeout` запросов, пока не сработает таймаут, плюс запас: один запрос на границе окна и
`rps × 100 мс` на то, что генератор освобождает место чуть позже дедлайна. Сумма по методам не
должна превышать `-max-in-flight` (по умолчанию 5000). Это проверяется до старта, ошибка называет
оба выхода: какой таймаут влезет и какой нужен потолок. Поэтому зависший сервис в потолок не
упирается: прогон доходит до конца, а отчёт говорит, сколько вызовов не получили ответа за
таймаут и после какого отправленного вызова цель больше не отвечала. Если потолок всё же кончился,
место держали дольше дедлайна больше чем на 100 мс — это генератор (не хватило процессора) или
отправитель, и отчёт объявляет прогон недействительным. Рядом печатается, сколько слотов в момент
упора держались после своего дедлайна.

## Пределы: pass

`pass` под вызовом говорит, при каких значениях прогон считается пройденным:

```yaml
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      pass:
        p99: 200ms
        errors: 1%
```

Все ключи — в [`examples/pass.yaml`](../../examples/pass.yaml), предел поиска — в
[`examples/breakpoint.yaml`](../../examples/breakpoint.yaml).

| Ключ | Предел |
|---|---|
| `p50`, `p90`, `p95`, `p99`, `p999` | Задержка не больше предела: длительность с единицей (`200ms`), целое число микросекунд, больше нуля, короче `timeout` вызова и короче часа. Нужен `errors` рядом: цель, которая мгновенно отвечает отказом, иначе проходила бы предел задержки. `p999` нужно 1000 измеренных вызовов: `rps` × (`duration` − `warmup`) |
| `errors` | Доля неудачных вызовов не больше предела: процент со знаком `%` (`1%`, `0.5%`), до трёх знаков после точки, не больше `100%`. Число без `%` не угадывается. `errors: 100%` снимает проверку отказов, и тогда пределы задержки ничего не стоят |
| `breakpoint.pass.held_rps` | Поиск должен удержать не меньше этого числа вызовов в секунду. Целое, одна из ступеней плана поиска. `pass` под вызовом вместе с `load.breakpoint` нельзя |

Конфиг с неверным `pass` — ошибка до старта (код выхода 1), а не прогон без проверки. Пустой
`pass: {}` — тоже ошибка.

**Вердикт на каждый предел**: `pass`, `fail` или `unknown`. Отчёт печатает блок `Thresholds:` с
худшим из них и строкой на предел; JSON — поле `thresholds`.

| Итог | Код выхода |
|---|---|
| Все пределы `pass` | `0` |
| Законченный прогон пропустил хотя бы один предел (`fail`) | `4`, `outcome` остаётся `complete` |
| Нет `fail`, но предел нельзя решить (`unknown`) | `2`, в `invalid_reasons` — `thresholds_undecided` |
| Прогон недействителен или остановлен | `2` или `3`, как без пределов: пределы их не меняют |

Пропуск сильнее нерешённого предела: при `fail` и `unknown` вместе код `4`.

Предел не решается (`unknown`), когда числу нельзя верить или его нет; причина — из закрытого
списка: `incomplete` (прогон остановлен), `invalid` (прогон недействителен), `few_observations`
(процентиль не измерен), `run_limit` (поиск упёрся в собственный предел прогона), `generator`
(опоздал генератор), `stream` (вызовы ждали свободный поток), `client_errors` (решают отказы
клиента, не цели), `nothing_sent` (не отправлено ни одного вызова), `censored` (в хвосте вызовы без
ответа за таймаут, значение — только нижняя граница, не выше предела).

- Задержка сравнивается в наносекундах, как её несёт JSON (`value.ns`): значение на наносекунду
  выше предела — `fail`, хотя `value.us` (обрезанное до микросекунды) может равняться `limit_us`.
  Нижняя граница выше предела — `fail`: настоящее значение ещё больше.
- Доля считает все неудачные вызовы и вызовы, не ушедшие из-за отсутствия соединения, от всех
  посчитанных. Для `fail` берутся только отказы, которые решила цель: запросы, отвергнутые
  клиентом, ошибки клиента и плохие ответы о цели ничего не говорят.
- Строка предела не противоречит вердикту: если значение, округлённое до трёх значащих цифр,
  оказалось бы не по ту сторону напечатанного предела, печатается точное. Рядом с FAIL это первое
  из трёх, которое выше предела: три значащие цифры, значение в целых микросекундах (к ближайшему;
  нижняя граница — вниз), значение до наносекунды (`100.4us` при пределе `100us`). Доля рядом с FAIL
  округляется к ближайшему, не вверх: берётся первое из 1, 2, 3 знаков после точки, при котором
  число больше предела (`1.004%` при пределе `1%`); если не хватает и трёх, печатается `> ` и
  предел как записан (`> 1%`).

## Доступ к сервису

```yaml
app:
  target:
    ip: 10.0.3.17
    port: 443
  ca: certs/ca.pem            # пути — относительно файла конфига
  cert: certs/client.pem
  key: certs/client.key
  server_name: payments.internal
  metadata:
    authorization: Bearer ${PAYMENTS_TOKEN}
    x-api-key: ${PAYMENTS_KEY}
```

**Секреты.** `${ИМЯ}` подставляется из переменной окружения, в том числе внутри значения:
`Bearer ${TOKEN}`. Переменная не задана или задана пустой — ошибка до старта с её именем. Иначе
ушёл бы `Bearer ` без токена, и прогон показал бы 100% отказов как вину цели. Чтобы написать
`${` буквально, удвойте доллар: `$${`. Одиночный `$` остаётся как есть. Подстановка работает
только в `app.metadata`: в `data`, `target` и остальных полях `${ИМЯ}` уходит как написано.
Флага для заголовков нет, поэтому токен не попадает ни в `ps`, ни в историю shell. Значения
заголовков инструмент не печатает нигде: ни в отчёте, ни в ходе прогона, ни в ошибках.

**Заголовки.** Имена приводятся к нижнему регистру, как их и передаёт HTTP/2. Ошибка конфига до
старта: ключ с `grpc-` (его резервирует gRPC), псевдозаголовки вроде `:path`, ключ с `-bin`
(бинарные заголовки пока не поддерживаются), `content-type` и `te` (их пишет сам транспорт),
`connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `upgrade` (в HTTP/2 их нет),
значение вне печатаемого ASCII. `user-agent` разрешён: цель увидит один заголовок, ваше значение и
после него ` grpc-go/<версия>`. Те же заголовки и
сертификат уходят в проверку методов перед стартом. Если цель на ней ответила `Unauthenticated`,
а заголовки заданы, прогон не начнётся: «target rejected credentials». `PermissionDenied` прогон
не останавливает: токен принят и может работать для вызовов, не пуская к reflection; методы
помечаются непроверенными. `Unauthenticated` без заголовков тоже не останавливает, а в заметке
сказано: «target requires credentials; app.metadata is not set».

**Сертификаты.** `ca` заменяет системные корни, а не добавляется к ним. Проверка сертификата
цели не отключается ничем. `server_name` меняет только имя, с которым сверяется сертификат и
которое уходит в SNI; `:authority` остаётся адресом из `target`. Зашифрованный паролем ключ не
поддерживается: его нужно расшифровать заранее.

**Соединения.** По умолчанию генератор держит одно соединение к одному адресу. Если DNS отдаёт
несколько адресов или цель стоит за L4-балансировщиком, нагружается только один бэкенд, и отчёт
этого не покажет. `app.connections: N` открывает N соединений. Имя, которое DNS
раскрывает в M адресов, разрешается один раз перед стартом, и соединение i идёт на адрес i mod M:
три соединения на два адреса — два и одно. Адрес, который не обслуживает цель (`localhost` в
`::1`, сервер слушает только `127.0.0.1`), останавливает старт и назван в ошибке: укажите его IP.
Блок отчёта показывает по соединению адрес, вызовы, долю отказов и p99, так что мёртвый или
медленный бэкенд за именем не усредняется. Повторов вызовов нет.
Service config от сервиса игнорируется: повторы и политика балансировки из него не применяются.
Боевой клиент, который их применяет, увидит другие категории и p99.

**Ошибки до старта.** Всё, что можно узнать до прогона, — код выхода 1 и ни одного вызова к
цели: файл не найден или не PEM, сертификат не подходит к ключу, сертификат цели просрочен или
не называет адрес (подсказка — `server_name`), цель закрыла соединение сразу после
рукопожатия (не приняла клиентский сертификат), TLS включён, а цель без него, или наоборот.

## Тело запроса

```yaml
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      data:
        wallet_id: "w-123"
        currency: USD                         # enum — по имени
        filter:
          since: "2026-01-01T00:00:00Z"       # google.protobuf.Timestamp
```

`data` — обычный YAML в форме сообщения. Схему инструмент берёт у сервиса через server
reflection; `.proto` не нужен. Тело собирается один раз до старта, и любая ошибка в нём —
неизвестное поле, не тот тип, несуществующий метод — видна сразу, с именем метода и поля, до
первого запроса. Нет `data` — уходит пустое сообщение, и reflection такому методу не нужен.

**Одно тело на метод.** Все вызовы метода уходят с одним и тем же `data`. Для записи с ключом
идемпотентности это значит, что первый вызов создаёт запись, а все следующие идут по пути повтора:
цель отдаёт уже сохранённый ответ. Меряется этот путь, а не создание записи.

Правила значений — стандартные правила JSON для protobuf (`protojson`):

- имя поля — как в `.proto` (`wallet_id`) или в JSON-форме (`walletId`);
- enum — по имени; `Timestamp`, `Duration` — строкой в их формате;
- `int64` и `uint64` доходят точно, в том числе больше 2^53 (snowflake-ID, суммы в минимальных
  единицах): число нигде не проходит через float;
- число с ведущим нулём (`0123`, `007`) — ошибка конфига: YAML прочитал бы его как восьмеричное.
  Нужен ноль — пишите строкой, `"0123"`;
- **`bytes` — строкой в base64.** `signature: abcd` — это не четыре байта `abcd`, а три других
  байта: `abcd` сам по себе валидный base64, и ошибки не будет. Четыре байта `abcd` пишутся как
  `signature: YWJjZA==`.

**Проверка методов.** Каждый метод из конфига проверяется у сервиса до старта: опечатка в имени
или метод, которого там нет, — ошибка до первого запроса, а не прогон, где все вызовы падают с
`Unimplemented`. Если reflection на сервисе выключен, метод с `data` не запустится — ошибка скажет
это прямо. Метод без `data` работает и без reflection: проверить его нечем, и об этом печатается
предупреждение — перед прогоном в stderr и ещё раз строкой в отчёте. В предупреждении сказано,
почему проверить не удалось: reflection выключен, ответил отказом или не ответил вовсе.

## Каждый раз другой запрос: dataset

```yaml
    - method: wallet.v1.WalletService/GetBalance
      rps: 800
      duration: 1m
      dataset: wallets.jsonl
```

```
{"wallet_id": "w-1", "currency": "USD"}
{"wallet_id": "w-2", "currency": "EUR"}
```

`dataset` — файл с телами запросов, по одному JSON на строку, в той же форме, что и `data`.
Относительный путь отсчитывается от каталога файла конфига. Первый запрос уходит с первой строкой,
второй — со второй, после последней строки — снова с первой. Пустые строки пропускаются. Файл
читается, и каждая строка проверяется по сообщению метода до старта — по правилам `data` и через
reflection; ошибка называет строку, `wallets.jsonl:3`, и никогда не печатает то, что в ней
написано. Файл без запросов — ошибка.

Под строкой метода отчёт говорит, сколько файла использовано:
`data: 3 of 3 requests from wallets.jsonl, each used up to 5 times`. Это сколько раз запрос отдан
отправителю, а не что увидела цель: запрос, который в файле стоит дважды, уйдёт дважды, а вызов,
не дошедший до цели, тоже посчитан. В поиске точки разрыва каждый шаг продолжает с того места, где
кончился прошлый, а строка считает весь поиск.

`dataset_order: random` отдаёт запросы в случайном порядке: каждый проход по файлу — новая
перестановка, в которой каждый запрос уходит один раз, поэтому цифры выше остаются прежними.
Строка тогда кончается словами `, random order, seed 42`. Чтобы повторить прогон, впишите это число
в `dataset_seed` (целое от 0 до 9007199254740991): тот же seed, файл и число запросов дают тот же
порядок. Не указан — seed выбирается при старте, свой у каждого вызова.

`dataset_reuse: false` отправляет каждую запись не больше раза, на вызов и на весь процесс:
прогрев, каждый шаг поиска и каждое соединение берут записи из одного счёта (два вызова с одним
файлом — два счёта). Строка тогда такая: `data: 3 of 3 requests from wallets.jsonl, each at most once`.
Прогон, который файл не покрывает, отклоняется до отправки, с обоими числами. Поиск, которому
нужна запись, а в файле её больше нет, останавливается как по Ctrl+C (код выхода 3): идущий
прогон не судится, отчёт называет файл и скорость. Только один процесс: записи не делятся между
машинами, а остановка оставляет записи неотправленными.

## Проверка перед нагрузкой

`leettest -c x.yaml -dry-run` (не выпущено) подключается и проверяет методы так же, как прогон,
затем шлёт по одному запросу на каждую запись `load.calls`, по очереди, в порядке конфига, и
печатает для каждой запрос в том виде, в каком он ушёл, статус и ответ в виде JSON. Нагрузки,
статистики и отчёта нет: за секунду видно, доходит ли конфиг до сервиса с этими данными и этой
авторизацией, до нагрузки, которая заполнила бы отчёт одной и той же ошибкой сто тысяч раз.

```
dry run: 2 calls, one request each, nothing measured
1/2 grpc.health.v1.Health/Check: success, OK, 1.20ms
  request: {"service":"wallet"}
  response: {"status":"SERVING"}
2/2 wallet.Wallet/Transfer: failure, InvalidArgument sent by the target, 800us
  request (record 1 of 500): {"from":"a-1","amount":"-5"}
  message: amount must be positive
metadata: authorization: Bearer ${TOKEN}, x-tenant: acme
```

- **Первая строка вызова:** имя категории, как в отчёте, код, кто его поставил (`sent by the
  target` или `set by the client`; у успеха ничего) и время от отправки до ответа. У вызова, к
  которому статус не пришёл (`unreachable`, `cut_off`), времени нет.
- **`request:` и `response:`** — байты, разобранные по схеме метода, в именах полей `.proto`,
  одной строкой. Запрос — то, что ушло по сети, поэтому поле со значением по умолчанию в нём
  отсутствует. У упавшего вызова вместо `response:` строка `message:` (текст статуса, только если
  он не пустой). Ответ, который не разбирается, печатается как `response: N bytes, not decoded:
  <ошибка>`, а категория вызова остаётся. Метод, которого reflection не знает, уходит пустым
  сообщением, с предупреждением в stderr, как в прогоне, и печатает `request: {}`.
- **Тело или сообщение длиннее 4096 байт** обрезается на этом месте и кончается
  `… (N bytes in all)`, где N — длина после того, как секреты скрыты. Управляющие символы
  сообщения записываются как `\xNN`.
- **Данные.** Вызов с `dataset` шлёт первую запись файла, что бы ни говорили `dataset_order`,
  `dataset_seed` и `dataset_reuse`; в блоке написано `record 1 of N`.
- **Метаданные** — одна строка после блоков: ключи в нижнем регистре, как уходят, по алфавиту,
  значения как написаны в конфиге, поэтому `${ENV}` остаётся нераскрытым. Нет метаданных — нет
  строки.
- **Секреты.** Значение каждой `${NAME}`, которую подставили в метаданные, заменено на `${NAME}`
  в `message:` и в `response:`: сервис, который отдаёт заголовок эхом, не вынесет секрет на экран
  и в лог CI, а ответ с ним читается `{"tenant":"${TENANT}"}`, а не `acme`. Не ловится секрет
  внутри поля `bytes` в base64. Секрет, записанный в самом YAML, печатается как записан, и в
  строке метаданных тоже: чтобы он не попал на экран, берите его из окружения через `${ENV}`.
- **Проверки как у прогона.** Что прогон отвергает до сети, то dry run отвергает с тем же
  текстом и кодом 1: файл короче, чем нужно плану, вызов сверх потолка запросов в полёте, метод
  дважды. `-max-in-flight` действует, как и `-c` и `-connect-timeout`. `-fake`, `-fake-delay`,
  `-fake-jitter`, `-fake-fail-ratio`, `-output`, `-json-file`, `-label` и `-plain` в dry run
  ничего не меняют и отвергаются: `-<имя> with -dry-run: …`.
- **Что конфиг говорит о нагрузке** — `rps`, `duration`, `load.ramp`, `load.warmup`, `pass`,
  `load.breakpoint` — принимается и не используется: конфиг с `load.breakpoint` получает по
  одному запросу на вызов и никакого поиска. У запроса каждого вызова действует его `timeout`.
- **Код выхода.** `0`, когда каждый вызов — `success`. Иначе `1` и в stderr `dry run: 1 of 2
  calls did not succeed`; тот же `1` — для всего, что останавливает прогон до старта (конфиг,
  файлы, недоступный сервис). Ctrl+C или SIGTERM отменяют вызов в полёте: напечатанные блоки
  остаются, больше ничего не шлётся, в stderr `dry run: stopped after K of N calls`, код `1`.
  Шаг CI читает `1` как «нагрузку не запускать».

## Остановка

`q` в полноэкранном виде, Ctrl+C без него:

- первое нажатие — новые запросы не уходят, запросы в полёте дорабатывают до своего таймаута и
  попадают в отчёт как обычно;
- второе — запросы в полёте обрываются и считаются отдельно как оборванные (`aborted`): не отказ
  сервиса, а нижняя граница времени; отчёт печатается;
- третье — выход сразу, без отчёта.

В полноэкранном виде верхняя строка ведёт по этим ступеням.

SIGTERM (`docker stop`, Kubernetes, отмена джоба в CI) сразу обрывает запросы в полёте и
печатает отчёт, минуя мягкую остановку: оркестратор через несколько секунд убивает процесс, и
отчёт должен успеть выйти. Если обрыв уже идёт, SIGTERM его не прерывает.

Остановленный прогон помечается в отчёте как неполный (код 3): числа в нём честные, но покрывают
меньше, чем было запланировано.

## Где запускать

На Linux рядом с целью: в той же сети, в том же кластере, на раннере CI. Всё, что лежит между
генератором и целью, входит в латенси и выглядит как время цели: на нашем стенде при 1000 RPS через
проброс портов Docker Desktop p99 был 38 мс, внутри сети Docker — 2 мс.

- Точное расписание вызовов — только на Linux. В контейнере с квотой CPU меньше двух ядер возможны
  редкие задержки старта до периода квоты (обычно 100 мс); отчёт их показывает.
- За L4-балансировщиком нагружается один бэкенд: одно соединение — один бэкенд. См.
  [как читать отчёт](../../README.md#как-читать-отчёт).
- На Windows часы идут шагами около 0,5 мс, и прогон с быстрым сервисом будет объявлен
  недействительным (`clock_step`, код выхода 2).

## Поля JSON

Правила контракта — версия схемы, единицы, `null` вместо `0`, неизвестные поля — в
[README](../../README.md#json-для-скриптов-и-ci). Здесь — каждое поле `schema_version` 1. Тип с `?`
может быть `null`. Счётчики прогрева не входят ни в какие другие счётчики; `sent` и все его доли
— только измеренные вызовы. В первой колонке — полный путь поля.

**Перцентиль** — объект; `null` — нет ни одного наблюдения. `<перцентиль>` — любое поле с типом
«перцентиль?» ниже.

| Поле | Тип | Что значит |
|---|---|---|
| `<перцентиль>.us` | int | Значение, целые микросекунды |
| `<перцентиль>.ns` | int | Значение гистограммы в целых наносекундах, которое текстовый отчёт печатает тремя значащими цифрами; `us` — оно же, обрезанное до микросекунд; по `ns` судят `pass:` и `leettest compare`: рядом с `fail` `us` может равняться `limit_us` |
| `<перцентиль>.lower_bound` | bool | `true` — это нижняя граница, а не значение ([README](../../README.md#как-читать-отчёт)) |

## Сравнение отчётов: `leettest compare`

`leettest compare [флаги] до.json после.json` читает два отчёта `-json-file` одного рода — два поиска
или два прогона — и печатает, что изменилось. Флаги идут перед файлами.
| Флаг | Что делает |
|---|---|
| `-max-capacity-drop` | Два поиска: предел падения ёмкости (`held_rps`) в процентах от ёмкости «до», например `10%`. Без него ёмкость печатается, но не судится |
| `-max-p99-rise` | Два прогона: предел роста p99 каждого метода в процентах от p99 «до», например `20%` |
| `-max-errors-rise` | Два прогона: предел роста доли неудачных вызовов в процентных пунктах, например `1%` |
| `-output` | Формат отчёта в stdout: `text` (по умолчанию) или `json` для скриптов и CI. Любое другое значение — код 1, файлы не читаются |

Коды выхода одни для обоих форматов: `0` — в пределах или пределов нет, `1` — отчёт не прочитан или
флаги не сошлись, `2` — отчёты несравнимы или предел нельзя решить, `4` — предел нарушен (и рядом с
проверкой, которую решить нельзя).

## JSON сравнения

`leettest compare -output json` пишет в stdout один объект и перевод строки, больше ничего; при коде
выхода 1 stdout пуст. Коды выхода и stderr те же, что у текста. В объекте собственные числа отчётов и
вердикты; процента изменения в нём нет — скрипт считает его сам из значений. Причина `unknown` —
значение из закрытого списка в `checks[].reason`, а `why` — те же слова, что печатает текст.

Имена методов записаны двумя способами. В `differences` и в тексте метод без ведущего `/`
(`pkg.Svc/Do`). В `checks[].method` имя такое, как в отчёте: у прогона с ведущим `/` (`/pkg.Svc/Do`),
у поиска без него.

Поле, которого у проверки по её виду нет, — `null`: у `capacity` пусты `*_p99` и `*_errors`, у `p99`
пусты остальные. Вердикт есть, только когда у проверки есть предел.

| Поле | Тип | Что значит |
|---|---|---|
| `schema_version` | int | Версия схемы, сейчас `1` |
| `mode` | string | Всегда `"compare"` |
| `compared_mode` | string | Род сравниваемых отчётов: `"run"` или `"breakpoint"` |
| `leettest_version` | string | Версия LeetTest, который сравнивал (не отчётов) |

Причины `unknown` — закрытый список; из первых шести побеждает первая подходящая:

- `not_comparable` — отчёты несравнимы, числа не сопоставляют;
- `method_invalid` — метод одной из сторон недействителен;
- `invalid` — прогон одной из сторон недействителен;
- `incomplete` — прогон одной из сторон не дошёл до конца;
- `generator` — одну из сторон держал сам генератор;
- `stream` — одну из сторон держал потолок потока;
- `few_observations` — замеров слишком мало для p99;
- `base_zero` — база равна нулю (p99 0 мкс или ёмкость 0 rps), доли от неё нет;
- `censored` — p99 упёрся в таймаут и не решает предел;
- `nothing_sent` — на одной из сторон ничего не отправлено;
- `client_errors` — решают ошибки самого клиента;
- `not_measured` — ёмкость одной из сторон не измерена;
- `broke_at_first` — поиск сломался на первой ступени, падения не видно;
- `lower_bound` — поиск кончился раньше отказа, ёмкость — нижняя граница.

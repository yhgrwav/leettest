# LeetTest в CI

[← К документации](README.md)

Эта страница показывает, как запускать нагрузочный тест при каждом изменении сервиса и
заваливать сборку, когда сервис перестал держать заданные пределы. Пример — workflow GitHub
Actions; любой CI, который запускает команды оболочки, делает те же четыре вещи:

1. Ставит LeetTest.
2. Запускает проверяемый сервис.
3. Запускает нагрузку. Код выхода — вердикт.
4. Сохраняет JSON-отчёт.

## Конфиг

`load.yaml` в репозитории сервиса. Пределы в `pass` делают код выхода вердиктом: без них прогон,
дошедший до конца, возвращает `0`, как бы сервис ни отвечал
([пределы pass](report.md#пределы-прогон-как-проверка)). `app.target` — сервис, который запустила
задача; в этом файле это эталонный стенд из нашего репозитория, цель нашего собственного CI.

```yaml
# Нагрузочный тест для CI. app.target — сервис, который запустила задача; здесь это эталонный
# стенд, из корня репозитория:
#   go run ./test/stand/cmd/stand -delay 20ms
#   leettest -c examples/ru/ci.yaml
# Пределы pass решают код выхода: на стенде оба держатся, поэтому он 0; пропущенный предел — 4.

app:
  target:
    ip: 127.0.0.1
    port: 50051
  tls: false

load:
  warmup: 2s
  calls:
    - method: wallet.v1.WalletService/GetBalance
      rps: 100
      duration: 10s
      pass:
        p99: 200ms
        errors: 1%
```

## Workflow

`.github/workflows/load-test.yml`:

```yaml
name: Load test

on:
  pull_request:

permissions:
  contents: read

jobs:
  load:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Install LeetTest
        run: |
          curl -fsSL https://raw.githubusercontent.com/yhgrwav/leettest/main/install.sh | sh
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
      - name: Start the service under test
        run: docker compose up -d --wait
      # example workflow: start
      - name: Run the load
        run: |
          rc=0
          leettest -c load.yaml -json-file report.json || rc=$?
          case "$rc" in
            0) ;;
            2) echo "::error::invalid run: the numbers are not about the service's load"; exit 1 ;;
            3) echo "::error::the run stopped before its plan"; exit 1 ;;
            4) echo "::error::a pass limit was missed"; exit 1 ;;
            *) echo "::error::leettest exited with $rc and no report"; exit 1 ;;
          esac
      - name: Read the report
        if: always() && hashFiles('report.json') != ''
        run: |
          echo "p99: $(jq '.methods[0].latency.p99.us' report.json) us" >> "$GITHUB_STEP_SUMMARY"
          jq -e '.thresholds != null and all(.thresholds[]; .verdict == "pass")' report.json
      - uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
        if: always()
        with:
          name: leettest-report
          path: report.json
          if-no-files-found: ignore
      # example workflow: end
```

Названия шагов и тексты ошибок в YAML по-английски: этот текст дословно совпадает с английской
страницей и с задачей нашего CI.

По шагам:

- **Установка.** `install.sh` кладёт последний релиз в `~/.local/bin` и проверяет его контрольную
  сумму ([установка](guide/first-run.md#установка)). Сборка, которая не должна меняться под
  ногами, фиксирует релиз: `LEETTEST_VERSION=<тег>` перед `sh`, тег — со
  [страницы релизов](https://github.com/yhgrwav/leettest/releases).
- **Запуск сервиса.** Замените шаг тем, как запускается ваш сервис, и направьте `app.target` в
  `load.yaml` на него. Нагрузка начинается сразу, как стартует LeetTest: дождитесь, пока сервис
  отвечает, до конца этого шага (для Docker Compose это делает `--wait`).
- **Нагрузка.** `-json-file report.json` пишет JSON-отчёт в файл, а текстовый отчёт идёт в лог
  задачи. `case` превращает каждый код выхода в одну строку ошибки; любой ненулевой код
  заваливает сборку. Файл создаётся до старта и никогда не перезаписывается, поэтому ему нужен
  чистый раннер.
- **Чтение отчёта.** `jq` достаёт из JSON одно поле: здесь p99 первого метода, в сводку задачи.
  Вторая строка проверяет, что пределы `pass` заданы и каждый выдержан: код выхода `0` у конфига
  без пределов о сервисе ничего не говорит. Шаг выполняется и после упавшей нагрузки, если файл
  есть.
- **Сохранение отчёта.** `if: always()` загружает его и для упавшего прогона. Прогон, который не
  стартовал (код выхода `1`), файла не оставляет, поэтому `if-no-files-found: ignore`.

Две строки-комментария `# example workflow` отмечают часть, которую наш собственный CI запускает
как написано.

## Коды выхода в сборке

| Код | Что случилось | Сборка |
|---|---|---|
| `0` | План выполнен, отчёт полный; с `pass` — все пределы выдержаны | проходит |
| `1` | Отчёт, который просили, не получен: прогон не состоялся или отчёт не записан | падает; причина в stderr |
| `2` | Прогон недействителен или предел `pass` нельзя решить | падает; это не прохождение |
| `3` | Прогон остановлен раньше плана | падает; отчёт — только о том, что прошло |
| `4` | Законченный прогон пропустил предел `pass` | падает; какой — в `thresholds` в JSON |
| `130` | Аварийный выход без отчёта после Ctrl+C | падает; отчёта нет |
| `143` | Аварийный выход без отчёта после SIGTERM | падает; отчёта нет |

`2` — не прохождение и не промах: числа в таком отчёте не про нагрузку на сервис, поэтому они не
могут показать, что предел выдержан. Отчёт называет причину (`invalid_reasons` в JSON):
генератору не хватило процессора, часы хоста слишком грубые, предел нельзя решить. Чинить надо
окружение; ослабление предела не помогает. Коды не меняются внутри версии 1.x:
[что не меняется](stability.md#коды-выхода).

## Чтение JSON

Текст отчёта — для людей, JSON и код выхода — для скриптов. Скрипт может опираться на поля и
значения со страницы [что не меняется](stability.md); все поля описаны в
[справочнике](reference.md#поля-json). Несколько полей, которые сборка обычно читает:

| Поле | Что в нём |
|---|---|
| `outcome` | `complete`, `invalid` или `incomplete`; тот же факт, что коды выхода `0`/`4`, `2`, `3` |
| `thresholds[].verdict` | `pass`, `fail` или `unknown` для каждого предела `pass` |
| `invalid_reasons` | почему прогон недействителен; у действительного пусто |
| `methods[].latency.p99.us` | p99 метода в целых микросекундах |

Скрипт пропускает поля, которых не знает, и не падает на новом значении перечисления.

## Где важен раннер

Нагрузка уходит с раннера, поэтому всё между раннером и сервисом входит в латенси, а раннер, которому
не хватает процессора, не удержит расписание: тогда отчёт говорит `generator_late`, а код выхода
`2`. Запускайте задачу рядом с сервисом, в той же сети или в той же задаче, и держите частоту в
пределах того, что раннер отправляет. Подробнее — [где запускать](reference.md#где-запускать) и
[чего числа не покрывают](limitations.md).

## Пример проверяется

Часть workflow между двумя комментариями-маркерами — это задача `example workflow` из
[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml), дословно;
[`examples/ci_page_test.go`](../../examples/ci_page_test.go) падает, когда они расходятся. Задача
идёт на каждом pull request, против эталонного стенда и сборки этого коммита. От workflow выше она
отличается только шагами перед отмеченной частью: страница ставит релиз и запускает ваш сервис,
задача собирает коммит и запускает стенд.

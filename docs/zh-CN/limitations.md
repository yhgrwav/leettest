# LeetTest 不做什么，以及它的数字在哪里不再成立

[← 返回文档](README.md)

> 译自 [docs/ru/limitations.md](../ru/limitations.md)，对应 3a9dbba，2026-11-10。如有出入，以俄文版为准。
> **可能滞后：** 中文版在每次发布前同步，最新内容请看[英文版](../en/limitations.md)。

LeetTest 只看得到客户端一侧：发出负载的机器和进程（下文称“生成器”），以及返回的结果。目标服务的资源它既
不知道，也不去猜。本页把各种边界集中在一处：在什么条件下报告里的数字说的不是目标服务，以及工具目前还做
不到什么。每一项的细节见它所链接的页面。

## 数字在哪里不再说的是目标服务

当生成器或到目标的路径破坏了测量时，报告要么自己说明，要么无法说明。下面逐项列出。

- **生成器的 CPU。** 生成器需要 CPU 才能按计划发出调用。如果不够（核数少、`GOMAXPROCS`、容器的 CPU
  配额），调用会晚于计划开始，这段时间计入延迟。当生成器的滞后决定了 p99 的尾部时，该次运行无效
  （`generator_late`，退出码 2），报告会列出相关方法，并建议给生成器更多 CPU、降低频率或把负载分到多台
  机器。每个方法从 100 个观测起才做判断；少于此数时 p99 就是最大值，运行仍然有效，只附一条说明。p99
  偏移不到 10% 不构成判定，只给出带数字的说明。断点搜索不会得到这个判定：它的各个阶梯有自己的原因
  `generator`。运行护照会显示 CPU 数、`GOMAXPROCS` 和配额。尚未发布：报告会指出生成器撞上的上限
  （`GOMAXPROCS`、CPU 配额、CPU 本身或调度），或说明无法指出；并且当生成器没有发出某个方法 1% 及以上的
  调用时，运行同样判为无效。
- **Linux 与 Windows 上的调度。** 精确的调用调度只在 Linux 上成立。在 CPU 配额不足两核的容器里，可能
  出现少量起始延迟，最长到配额周期（通常 100 毫秒）；报告会显示。在 Windows 上时钟以约 0.5 毫秒的步长
  走动，对快速服务的运行会被判为无效（`clock_step`，退出码 2）：时钟比 p50 的四分之一还粗，或运行期间
  步长增长到 1 微秒及以上。请在 Linux 上、紧挨着目标服务运行。
- **生成器与目标之间的网络。** 两者之间的一切都计入延迟，看起来就像目标服务的耗时。工具不单独知道网络
  延迟，也不对此下判断。在我们的测试台上，1000 RPS 时经 Docker Desktop 端口转发 p99 为 38 毫秒，在
  Docker 网络内部为 2 毫秒。
- **L4 负载均衡器。** 默认情况下所有负载走一条连接，这条连接落在某一个后端上：位于 L4 均衡器之后
  （Kubernetes 的 ClusterIP、NLB），以及 DNS 返回多个地址时都是如此。“扛不住 X”说的是这个后端，而不是
  整个服务，报告对此不会显示。要给多个后端加压，请设置 `app.connections`：报告会为每条连接给出一行。
  能把单个请求分散开的 L7 均衡器（Envoy、gRPC ingress）同样会分散单条连接上的请求。
- **目标的流配额。** 目标声明单条连接上最多能同时有多少个调用在途（`MAX_CONCURRENT_STREAMS`）。拿不到
  流的调用在客户端等待，这段等待计入延迟。如果尾部的原因是流用完了，报告会这样说明并给出不含等待的
  p99，但目标的容量超过“上限 × 连接数”的部分并未测量。
- **在途调用的上限。** `-max-in-flight`（默认 5000）限制正在等待响应的调用。各方法的 `rps × timeout` 之和
  再加余量，会在启动前与它核对，所以挂死的目标不会撞到上限。如果上限仍然耗尽，说明是生成器占着名额
  （它的处理器不够），该次运行无效。
- **无效运行会点名什么，不点名什么。** 它给出封闭列表中的原因和方法。它不指出目标的瓶颈，不区分目标的
  CPU 与它的数据库，也不判断客户端看不到的事情。
- **错误类别。** 状态码可能来自目标前面的代理，而不是目标本身：没有存活后端的 nginx 会回 `UNAVAILABLE`，
  客户端无法区分。请求过大是靠 grpc-go 的错误文本识别的；使用其他实现的目标（Envoy、Java）写法不同，
  拒绝会被归入 `overload`，而不是 `request error`。
- **样本太小。** 观测数少于 100 时 p99 就是最大值。关于生成器的判定知道这一点，但 `leettest compare`
  和针对 p99 的 `pass` 限值会不加说明地用这样的 p99 来判断。
- **关于生成器的判定很脆弱。** 在 200 个观测时，p99 的尾部只靠两个调用撑着：一个晚开始 4–35 毫秒的
  调用就可能让运行变为无效。数字不说谎，但这样的样本上的判定是脆弱的。
- **“over time”窗口。** 它们的 p50 和 p99 只给两位有效数字，因此不拿它们与整次运行的 p50 比较到最后
  一位。窗口占内存：每个“方法 — 窗口”对约 74 KB，50 个方法时约 250 MB。预热直方图每个方法约 600 KB；
  方法多且都带预热时，内存会叠加。

## 目前还做不到的

- **只支持 unary 调用。** 流式方法在加载时被拒绝。
- **调用串联。** 不能把一个方法响应里的字段填进另一个方法的请求——已列入计划，见[调用串联](chaining.md)
  和[路线图](roadmap.md)。
- **长时间运行中刷新令牌**——已列入计划，见[路线图](roadmap.md)。
- **未设置 `dataset` 时，同一方法的每次调用都发送同一个请求体。** 设置 `dataset` 后请求各不相同，但这
  并不表示目标服务看到了同样多种不同的请求：报告中的 `data:` 行会显示文件里用到了多少条请求。
- **不支持 `-bin` 头**（二进制头）。
- **不支持带密码的私钥：** 请事先解密。
